## A. Statistical validity of the ranking and the fp8 comparison

**A1. Timeout censoring is quant-dependent and will deflate Q3_K_M for speed, not quality — the ranking's core confound. HIGH.**
The controlled config holds ctx/KV/FA/thinking/timeout constant, but at 15–22 tok/s (plan-2026-09-03.md:52 "Q3_K_M longer (spills to CPU at this config, 15-22 tok/s)") a Q3_K_M turn that Q2_K_L finishes in 450 s takes ~1,100–1,500 s of generation alone, against a 1800 s cap shared by all quants. Observed Q2_K_L runs are ~450 s single-turn 24 k-token dumps (results/v4-local-medium.log:2-4). Q3_K_M will systematically hit the cap on exactly the tasks where it tries to work; `v4-analyse.py:17-18` scores a timed-out non-pass as `score or 0.0`, so censored runs drag its mean toward 0 regardless of quality. The overnight plan explicitly blessed this ("Its slowness costs time, not validity", overnight-plan-2026-09-03.md:20) — that claim is wrong when the timeout binds.
*Fix:* no code change needed — in the report, present mean SCORE **with the timeouts column adjacent and a conditional mean over non-timeout runs** (v4-analyse.py already prints both; the control session just must not headline the uncensored mean). If Q3_K_M shows ≥3 timeouts, mark its score "censored, lower bound" and rank Q2_K_L vs Q3_K_S as the only clean comparison.

**A2. The fp8 "reference" runs under a materially different harness config than the locals — the delta is not a clean upper bound on quant loss. HIGH.**
The ranking uses agent dir `pi-agent` (pibench.py:23, AGENT_DIR default at pibench.py:301 `agent_dir = a.agent_dir or (AGENT_DIR if a.provider == "ollama" else "")`); the ref script forces `--agent-dir "$PWD/results/pi-agent-v4"` (v4-ref-1800.sh:9). The two dirs differ in more than provider:
- `pi-agent/settings.json`: `"compaction": { "enabled": false }`, plus an explicit `retry` block (`timeoutMs: 900000, maxRetries: 0`).
- `results/pi-agent-v4/settings.json`: compaction **enabled** (`"reserveTokens": 548576, "keepRecentTokens": 20000`) and **no retry block** → pi's default retry policy applies.
- Locals get `"maxTokens": 32768` pinned in pi-agent/models.json; pi-agent-v4/models.json contains only OpenRouter routing overrides for qwen — no maxTokens, no contextWindow pin, so fp8 gets whatever OpenRouter advertises, with a much smaller per-turn output cap than the locals' 32 k.
The overnight plan acknowledged only "a different max_tokens/provider" (overnight-plan-2026-09-03.md:24); compaction and retry differences are unacknowledged, and live plan line 45 ("maxTokens = contextWindow in pi-agent/models.json") describes only the local side. A 34-turn, 75 k-output fp8 run (v4-ref-medium-1800.log:3) is exactly where compaction/keepRecentTokens-20000 changes the model's own context content.
*Fix:* none applied mid-run (both streams are already committed to their agent dirs and the streams are unresumable across agent-dir changes). Quantify the confound after the fact: read both settings files into the report as a stated caveat, and report the fp8 delta as "upper bound on quant loss *under unequal serving configs*", dropping the word "controlled" from the fp8 comparison. Do not let the report claim parity it doesn't have.

**A3. The ranking will almost certainly end "tied" and the report's headline deliverable evaporates. MED.**
7 tasks × 3 trials = 21 samples per quant; v4-analyse.py bootstraps over 7 task means (v4-analyse.py:35-41) and declares SEPARATED only when two 90 % CIs don't overlap at all (v4-analyse.py:52-53, `a[2] > b[3]`). Marginal-CI non-overlap with n=7 is an extremely conservative criterion, and the comparison is unpaired even though both quants run the *same* tasks — the shared rng (`Random(12)`, v4-analyse.py:13) draws independent resamples per model instead of resampling task indices once and differencing, which is where the power lives. Adjacent quants (Q3_K_S vs Q3_K_M) will almost certainly tie.
*Fix:* the control session can run a paired analysis without committing anything: instruct that the final report use the per-task table (already printed by v4-analyse.py) and, if desired, run a one-off paired bootstrap in a throwaway command (`python -c` in a shell) that resamples task indices once and computes the CI of the *difference*. Label any SEPARATED from the shipped script as "conservative marginal test". Also state up front on the phone that "tied" is the likely outcome so a null result isn't read as a broken run.

**A4. `v4-analyse.py` mixes censored and uncensored evidence between its own two metrics. LOW.**
`passes` excludes timed-out passes (v4-analyse.py:43) but the mean SCORE includes them (v4-analyse.py:16-21 falls through to `s` when `timed_out and pass`). A timed-out-but-graded-PASS run counts as 1.0 in the mean and 0 in the pass column. Edge case, but it makes the "pass implies SCORE 1.0" bookkeeping (overnight-plan-2026-09-03.md:30) false in one direction.
*Fix:* when relaying numbers to the phone, note the two metrics can disagree for timed-out passes; no script edit needed.

**A5. Q2_K_L's three trials are deterministic carbon copies — "3 trials" is illusory replication for the degenerate quant. LOW (observation, not a bug).**
All three 52_reengine trials: identical `out=24151`, turns=1, tools=0 (v4-local-medium.log:2-4). Trials carry zero within-task variance for this model, so per-trial averaging adds no information; only task-level spread matters. The bootstrap CI (over tasks) is therefore the right instrument — but any verbal claim of "3 independent trials" for Q2_K_L overstates it.
*Fix:* say "task-level replication" in the report, not "trial-level".

**A6. Keep-filter evidence at 1800 s can retroactively reject a keeper mid-ranking, and no trigger exists for that. MED.**
Plan §3b says the ref provides "the keep-filter evidence at 1800 s for 52 … and 55/56/57/59/60/61" (plan-2026-09-03.md:53-54) under the rule "0 or > 0.85 rejects" (plan-2026-09-03.md:73). First datum: fp8 **timed out** on 52_reengine at 1800 s (v4-ref-medium-1800.log:3, `1803.0s … TIMEOUT`), scoring ≈0 — by the letter of the keep filter, 52_reengine should now be rejected. There is no defined action for this: the ranking keeps running 52 for all three quants (correctly, for the quant-vs-quant comparison), but the report's "v4 separates quants" story now rests partly on a task the filter says is unfair at 1800 s.
*Fix:* when relaying 52's fp8 result, send the owner the contradiction explicitly and report the ranking both ways (all 7 tasks; and excluding 52 if its fp8 mean lands at 0 from pure timeout). Precede the keep-filter clause in the report with "at 1800 s, timeouts dominate" rather than silently re-applying the 1500 s-era number 0.677.

## B. Failure modes in the live streams

**B1. One transient `usage()` failure kills the entire fp8 reference stream and mislabels it "CAP REACHED". HIGH.**
v4-ref-1800.sh:11-14: `NOW=$(usage)` — if the OpenRouter auth-key endpoint hiccups (rate limit, network blip), `NOW` is empty and `python -c "print(round($NOW-$BASE,4))"` raises, leaving `SPENT` empty; line 14 then evaluates `0 if  < 9.50 else 1` → SyntaxError → exit 1 → the `||` branch fires and the script logs **"CAP REACHED"** and exits, having spent far less than the cap. Same failure if `BASE` (line 7) were ever empty. The stream cannot be restarted idempotently by the wrapper — it would have to be relaunched task-by-task.
*Fix:* the control session cannot safely edit a bash script that is mid-execution (bash re-reads running scripts from disk at byte offsets). Instead: monitor the ledger (results/v4-ref-ledger.txt) — a new "after <task>" line appears only after each 3-trial block (~30–90 min); if a "CAP REACHED" line appears while ledger spend is well under 9.50, treat it as a false trip and relaunch the *remaining* tasks as individual pibench invocations with the same tag (pibench resumes from the JSON, pibench.py:292-294), with the cap check done by hand.

**B2. Cap enforcement granularity is one 3-trial task block, and the ledger is silent for ~90 minutes at a time. MED.**
The spend check runs only after a whole task block (v4-ref-1800.sh:9-14); the first ledger line after baseline will not appear until ~3 × 1800 s after 09:32. With fp8's observed 75 k output tokens/run (~USD 0.17 output alone at 2.20/M), a block can overspend the 9.50 cap by roughly USD 1–2 before the check fires — brushing against the owner's "USD 10 additional budget" (plan-2026-09-03.md:15).
*Fix:* the control session can poll `curl https://openrouter.ai/api/v1/auth/key` directly on its own cadence and, if spend crosses ~9.00 mid-block, drop `results/STOP_RANKING`-equivalent action by killing the ref pibench tree at a trial boundary (results JSON is written after every run, pibench.py:319) and reporting partial coverage.

**B3. Stop markers are checked at quant boundaries only — up to 10.5 h of unattended running after an alert, contradicting the plan. MED.**
Plan claims "results/STOP_RANKING (graceful, checked at task boundaries)" (plan-2026-09-03.md:48), but v4-local-ranking.sh:5-6 checks both markers only at the top of the per-quant loop (v4-local-ranking.sh:4). pibench itself has no marker check. An alert fired at 10:15 during Q2_K_L would not stop anything until Q3_K_M's block ends — potentially into the next morning.
*Fix:* on any ALERT, the control session should not wait for the marker logic: kill the ranking python tree (`pwsh Stop-Process -Id … /F` on the pid from results/ranking.pid — but note pibench's pid is the *python* child; use the process tree). Resumption is safe and lossless: pibench reloads results/v4-local-medium.json and skips completed (task, trial) pairs (pibench.py:292-294), so a mid-quant kill costs at most one in-flight run. Record the kill in env-changes.log and relaunch at the next boundary.

**B4. Watchdog goes blind exactly when a VRAM leak is most likely: `models="?"` suppresses the VRAM alert. LOW.**
gpu-tune/watch.sh: `models=$(curl … || echo "?")` — when the Ollama API is unresponsive (the symptom of a wedged server), `models` is `"?"` and the alert condition `[ "$models" = "0" ]` (watch.sh:18) never fires, so "VRAM held with a wedged API" is invisible. The free-RAM alert still works. Also note the alert file is appended every 60 s while the condition persists — a stale `results/gpu-watch.ALERT` from a *transient* event will kill the ranking at the next quant boundary even if the condition has cleared, unless someone deletes the marker (the plan's §3d does cover deleting it for transients, plan-2026-09-03.md:63).
*Fix:* none needed on the running watchdog; the control session should simply treat `models=?` streaks in gpu-watch.log as an alert-equivalent and check `/api/ps` manually.

**B5. The "===== q27-…" trigger fired ambiguously at 09:28 and will fire on a one-row table. LOW.**
The log's first line is already `===== q27-Q2_K_L =====` (v4-local-medium.log:1) — if Monitor blei9ivzk matched on it, the "run v4-analyse and send" trigger (plan-2026-09-03.md:50-51) produced a table with zero models (analyse skips models with no runs, v4-analyse.py:29-31). The trigger as written can't distinguish a block start from the previous block's completion.
*Fix:* re-anchor the trigger to the `=== <model> exit=` lines the wrapper writes (v4-local-ranking.sh:7), which appear only at block completion; if a premature empty table was already sent to the phone, send a one-line correction.

**B6. Sonnet verification target (21 entries) doesn't match reality yet — and the plan's own count is uncheckable against batch pacing. LOW.**
results/sonnet-v4/grades.json currently holds 12 entries (52/t1-t3 + …), plan expects "verify grades.json counts (21 entries) against sandboxes" (plan-2026-09-03.md:59). Not a fault, but the trigger will under-count if fired on overseer completion while late batches grade.
*Fix:* at overseer completion, recount and, if <21, wait for the sandboxes' grades.json to fill before sending the table; treat a long-empty output file as a blocked prompt per the owner's 09:52 note (plan-2026-09-03.md:60).

## D. The mid-run 59_uri test.py rewrite and the vacuous oracle

**D1. Mid-run grader mutation is structurally possible and the plan's safety argument rests on a timing accident, not a mechanism. HIGH (as a class of failure).**
pibench stores the test *path* at load time and copies it at grade time (pibench.py:213 `shutil.copy(task["test"], …)`), so any write to `tasks-v4/*/test.py` between load and grade silently changes scoring for every later run. This actually happened: test.py mtime 09:43:42, ranking started 09:28. It happens to be benign only because no live stream had graded 59_uri before 09:43 (confirmed: local JSON has 52/55 runs only; ref log has 52 trial 0 only; smoke.log's own 09:50 note says the same). Nothing prevents a recurrence — the stale-author class of subagent is still alive in principle until tonight ends.
*Fix:* the control session should (a) verify no author subagents remain (check for any live session writing under tasks-v4), and (b) snapshot integrity now, without commits: `sha256sum tasks-v4/*/test.py > results/v4-test-hashes.txt` and re-check before each quant boundary. Any hash change mid-stream = kill, assess, relaunch (resumable). This costs nothing and converts an invisible confound into a detected one.

**D2. The 09:43 test.py has never been validated by anything: no selftest, no Haiku gate, and it carries its own 45 s internal watchdog inside pibench's 60 s grader cap. HIGH.**
The Haiku numbers for 59_uri (19/27, 27/27, 26/27) were produced by the *old* test (smoke.log note; plan-2026-09-03.md:57 admits this). The new 29,737-byte differential grader (imports the candidate `uriref`, embeds an `_o_*` oracle, 27 checkpoints, threading, `Timer(45.0)` internal watchdog — test.py:1-40) has never graded anything. Failure modes: (a) an environment bug → grader exits nonzero with no SCORE → every model scores 0.0 on 59_uri via `score()`'s `None → 0.0` path (v4-analyse.py:16-21), silently; (b) the 45/60 s budgets are tight for a 27-checkpoint threaded differential test — a slow model whose grader thread stalls gets 0, not partial credit; (c) pibench's pass rule `grc == 0 and "PASS" in gso` (pibench.py:266) means a grader crash after printing a SCORE line still records partial score but no pass — inflating mean SCORE while the pass column stays honest.
*Fix:* the control session can validate it offline right now: copy `tasks-v4/59_uri/{seed,ref,test.py}` into a scratch temp dir, place `ref/uriref.py` as the candidate, run `_hidden_test.py` once (a 45 s grader execution, not a benchmark/model run), and confirm it prints `SCORE 27/27 … PASS` and exits 0. Also confirm the *seed* candidate fails (differential sensitivity). If the reference itself doesn't score 27/27, the task is broken for every model tonight — then exclude 59_uri from all reporting (the plan already plans "with and without 59_uri", plan-2026-09-03.md:52) and delete the task from the *report*, not from tasks-v4 (never touch task files mid-run).

**D3. "Vacuous oracle" is now half-true, and the report must not call 59_uri a differential task without qualification. MED.**
The new test embeds an oracle that is a renamed copy of the reference behavior (`_o_parse/_o_resolve/…`, test.py:337-350) — exactly what the plan flags ("its oracle is a renamed copy of the reference, so the differential buckets are vacuous there", plan-2026-09-03.md:52, and §7, line 100). Consequence: 59_uri can only measure "matches the reference implementation", it cannot detect reference bugs, and its per-quant numbers are not comparable in kind to the other six tasks' failure-mode tests. Cross-probe comparability is additionally broken for Haiku (old test) vs everything else (new test).
*Fix:* in the report, present 59_uri in a separate row/footnote: "reference-match test, rewritten mid-experiment 09:43, Haiku numbers not comparable"; keep the headline ladder computed without it (primary), with it as a sensitivity row (secondary). Do not count 59_uri toward any "tasks that separate quants" claim.

## Verdict

The ranking's machinery is better than typical for this kind of overnight effort — incremental JSON persistence with lossless resume, process-tree kills, a watchdog with a real alert path, and a bootstrap CI over the right unit (tasks) — but the night has three genuine threats the plan currently misstates or misses: the fp8 comparison is not the controlled parity the report language assumes (different agent dir with compaction enabled, unpinned maxTokens, default retries, and a 1800 s cap under which the strongest model already timed out on its flagship task), Q3_K_M's spilled speed will convert the 1800 s timeout into a quality score penalty the "costs time, not validity" claim doesn't cover, and the live streams' stop/cap logic has two silent-death modes (one failed `usage()` call ends the fp8 stream as a fake "CAP REACHED"; stop markers bind at quant, not task, boundaries, leaving up to 10.5 h of unattended running after an alert). The 59_uri rewrite turned out benign by timing accident rather than by design, and the new grader is completely unvalidated with tight 45/60 s budgets — a one-off offline grader run plus a hash snapshot converts that from a hope into a check, and the same snapshot discipline should extend to all seven test.py files tonight. None of this requires commits, config changes, or touching the running processes: the control session's highest-value moves in the next hour are (1) snapshot test.py hashes, (2) validate the 59_uri grader offline, (3) set report-language expectations now — "tied is likely, Q3_K_M may be censored, fp8 delta is confounded, 59_uri is reference-match only" — and (4) watch the ref ledger for a false CAP REACHED, with kill-and-resume (which pibench makes lossless) as the standing response to any alert. Run the ranking; just stop planning to describe it as more controlled than it is.
