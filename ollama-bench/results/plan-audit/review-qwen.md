

Adversarial review of `plan.md` (with ground truth from `brief.md`, `ollama-bench/pibench.py`, `pi-agent/models.json`, and prior `results/*.json`).

1. **HIGH — the v4 quality command's `--num-ctx` is a no-op.** In `pibench.py`, `num_ctx` is only consumed by `tps()` (the `/api/generate` probe). `run_pi()` never passes it to Ollama, and the plan adds `--no-tps`, so "Q2_K_L @ 32k / Q3_K_S @ 32k / Q3_K_M @ <its ctx>" is not actually set — the runs use whatever `OLLAMA_CONTEXT_LENGTH`/Modelfile default the server has (4–8k). Every quality run in the core deliverable would execute at the wrong context. **Fix:** toggle Ollama env per quant and verify with `/api/ps` before each quant's pass (the env-toggling the plan already permits).

2. **HIGH — the "3/3 with mean SCORE < 0.9" keep-filter branch is unreachable, so the filter is just "keep 1/3–2/3" on 3 coin flips.** Brief rule 1 requires `PASS` only when *all* cases pass, and `pibench.run_pi` defines pass as `rc==0 and "PASS" in stdout` — a 3/3 PASS task has SCORE = m/m = 1.0 in all three trials, so mean SCORE < 0.9 can't hold. Consequence: at n=3, a task with true p=0.5 is rejected 12.5% as 3/3 and 12.5% as 0/3 (~25% misclassification); p=0.6 rejected 22%. On 12 candidates, expect ~3 useless rejections/author rounds, and the "12 candidates → ≥8 keepers" budget is tight; "stop at 10" (10 what?) also conflicts with "two extra rounds" and is undefined. **Fix:** replace the branch with a score-based band (e.g., keep iff mean SCORE ∈ [0.3, 0.85] across 3 trials, reject above/below) and define "stop at 10".

3. **HIGH — ranking quants at 2 trials each is statistically noise, and the 3rd pass is optional.** With 10 tasks × 2 trials, the pass-rate SE per quant is ~0.06–0.08; typical Q2_K_L-vs-Q3_K_S quality gaps on this kind of suite are smaller than that. "Third trial pass if time allows" makes the headline deliverable (ranking) conditional, and the plan even compares 2-trial locals against a 3-trial reference. **Fix:** make 3 trials mandatory for any quant that appears in the ranking, and rank primarily on mean SCORE (partial credit gives 30 samples, not 10–20 binary ones).

4. **HIGH — the "morning report" can't contain its first line.** The report to phone@fractal leads with the quality-vs-speed ranking, but the 2-trial v4 pass finishes ~14:00 and a 3rd trial ~18:00–21:00 (or never). An overnight plan whose report is due in the morning promises a result that doesn't exist yet. **Fix:** reschedule the report to after the 3-trial pass, or explicitly split it: morning = tuning + authoring, ranking follows when ready.

5. **MED — different `num_ctx` per quant confounds the ranking.** Q3_K_M runs at its largest fully-resident ctx (possibly 16–24k) while the others run at 32k. Context headroom changes failure mode, not just quant quality: `pi-agent/models.json` hardcodes `contextWindow: 32768` for *all* models, so at 16–20k the agent believes it has 32k and hits server-side overflow mid-task (an error event, not a quality signal) exactly when v4 tasks need "~20–30k of context per turn" — the same threshold at which the plan skips Q3_K_M. **Fix:** run all quants at one common ctx (min of the resident set) for the ranking, or update `models.json` per quant and report the ctx-confounded numbers separately as "at-best-config".

6. **MED — the fp8 reference is uncontrolled for the serving stack.** The reference is OR qwen3.8-27b (managed `~/.pi/agent` config) while locals run through Ollama's OpenAI-compat endpoint with the bench agent dir, hardcoded `maxTokens: 16000` and `contextWindow: 32768`. Any local shortfall vs the OR reference conflates quant degradation with harness/serving/maxTokens differences — and there is no local fp8 control run in the plan to bound that. **Fix:** add one local fp8 1-trial spot-check (or at least match `maxTokens`/contextWindow across both configs) and state the delta is a ceiling, not a measured gap.

7. **MED — "VRAM/RAM logged at every model load/unload" is not actually logged in the quality runs.** The only VRAM capture in `pibench.py` is `gpu_split()` inside `tps()`, which `--no-tps` disables — so during the 10-hour v4 quality pass (the part that matters) the harness records no VRAM at all, and the leak-stop rule only fires at (quant, suite) boundaries, i.e., ~3 h after a slow leak starts. **Fix:** run a continuous 1 Hz `nvidia-smi`/process-RAM sampler to a log file for the whole night and check it at each task boundary, not just model swaps.

8. **MED — "one model on the GPU" is structurally unenforced.** The rule is only respected if the single Ollama process is the only consumer; nothing in the plan kills a stray `ollama run`, jupyter, editor preview, or a leaked `llama-server` from an earlier probe, and two models resident (even briefly during a swap) would silently corrupt every VRAM/residency conclusion. **Fix:** assert at every probe/run boundary that `/api/ps` shows ≤1 model and `nvidia-smi` has a single GPU-process, abort otherwise.

9. **MED — "never idle" has a hole between filler exhaustion and v4 ready.** Step 2's filler is finite (2 KV@64k + 2×4 ctx ladders + 2×6 fill curves + 1 fine-tune ≈ 20–30 probes); if it finishes before the 05:00 v4 handoff (plausible: each probe is minutes), the GPU idles with no defined fallback. **Fix:** define a loop filler (repeat the KV/ctx matrix on the other quant, or pre-run one v3 local-medium trial pass) that auto-starts when the list is exhausted.

10. **LOW — `--num-ctx <ctx>` in the v4 command line is silently misleading even after fix #1.** Operators reading the log will believe the ctx is per-run; it isn't (harness limitation). **Fix:** annotate the command with `# ctx set via OLLAMA_CONTEXT_LENGTH, verified in /api/ps` or extend `run_pi` to send `options.num_ctx`… (no file edits per your constraint — the log annotation is the in-scope fix).

11. **LOW — `load_tasks()` crashes the whole stream on any stray directory in `tasks-v4`.** It unconditionally `open(prompt.md)` for every subdirectory; an in-progress authoring scratch dir (or `tasks-v4-rejected` accidentally placed inside) kills the 05:00 launch, hours into the night. **Fix:** pre-flight `selftest2.py` plus a check that every subdir has `prompt.md` + `test.py` before launching (the handoff criterion already runs selftest2 — add the layout check).

12. **LOW — ETA arithmetic is internally consistent but the "~8 min/run" basis is stale.** Measured wall/run on the last local medium pass was 47–107 s average (max 475 s, 0 timeouts), so 3 h/quant is 4–10× conservative *if* v4 is as easy for the model as v3 was (which saturated 46/48 — v4 tasks that fail may still be fast to attempt, but 30-min-timeout runs on weak quants are the real tail risk: 20 runs × 30 min = 10 h worst case per quant). **Fix:** track running wall/run after the first 4 tasks and re-forecast the 3-trial pass; if pace allows, promote 3rd trials from "if time allows" to required.

13. **LOW — OR stream concurrency cap is unenforced.** Step 5 (running), step 4 (finishing ~02:00), and the keep-filter pibench all target OR; "at most 2 concurrent pibench processes" is a rule with no mechanism, and the keep-filter trials double as the reference — a third concurrent run degrading OR latency could push borderline tasks across the 60 s grader/1800 s timeout and corrupt `v4-ref-medium.json`. **Fix:** serialize: wait for step 5's file to be final before starting any keep-filter pass.

14. **LOW — `gen tok/s at its config` for the report won't be in the v4 result files.** `--no-tps` means the `v4-local-medium` tag has no TPS block; the report must manually join speed numbers from the tuning results, and the tuning was measured at probe configs (q8_0 KV etc.) that must match the quality-run config exactly or the number is meaningless. **Fix:** pin the speed numbers to the exact (quant, KV, ctx) tuple used in step 3 when writing the report.
