# OpenRouter smoke — four models vs GLM 5.3 Flash, v5 tiny band, 2026-09-05

One trial of the v5 tiny band (`results/v5/authoring/round2/suite-0`, 8 tasks) per model,
all four models in parallel through `pibench.py --provider openrouter`. The GLM 5.3 Flash
reference row is the identical run from
`results/pirun/pirun-baseline-2026-09-05.md` (tiny band).

Verdict rule as briefed: **eliminate** on any refusal, tool-call failure, systematic error,
or 2 or more passes below GLM (i.e. 3/8 or worse); otherwise **keep**; **inconclusive** if the
arm did not produce a usable result. All four arms completed all 8 tasks with exit 0, so no
arm is inconclusive.

- `upstage/solar-pro4` — **eliminate**. One task (g01) hit the 300 s wall clock cap and was
  killed with the last stop reason `toolUse`, having emitted 16,525 output tokens in only 3
  turns; that is a task the arm did not finish, not a graded failure. It is also the slowest
  arm by summed wall (796.0 s, 5.3x GLM) and spends 4.7x GLM's output tokens, with t02 taking
  175.1 s against GLM's 7.8 s on the same task.
- `inclusionai/ling-3.0-flash` — **keep**. Best pass rate in the pass at 7/8, two above GLM;
  the only failure is g01. Its two error rows are provider-side and transient (a 13,351 ms
  provider timeout on g03, and 429 rate-limit responses on g03 and t03 reading
  `inclusionai/ling-3.0-flash is temporarily rate-limited upstream`); both tasks still passed,
  and neither is a refusal, a tool-call failure or a model-side fault. The rate-limiting is
  an availability question for a second run, not an elimination on this run's criteria.
- `nvidia/nemotron-3-nano-30b-a3b` — **keep**. Level with GLM at 5/8 and zero errors. It
  passes g03, which GLM fails, at the cost of 241.6 s over 44 turns and 43 tool calls. It is
  by far the heaviest arm on tokens: 912,013 cumulative input (6.0x GLM) and 98,630 output
  (8.2x GLM).
- `inception/mercury-2.5-preview` — **keep**. One pass below GLM at 4/8, zero errors, and the
  fastest arm in the pass by a wide margin: 46.4 s summed wall against GLM's 149.2 s, with
  every task under 10 s. Token use is close to GLM's on both sides.

## Exact commands

Scratch clone made first, from WSL:

```
git clone /mnt/d/local-llm-bench /mnt/c/Users/slb/bench-orsmoke
```

Agent directory copied from the managed Windows pi agent dir, minus `auth.json` and
`sessions`, so nothing touches the managed copy:

```
mkdir -p /mnt/c/Users/slb/bench-orsmoke/ollama-bench/results/pi-agent-smoke
rsync -a --exclude auth.json --exclude sessions/ \
  /mnt/c/Users/slb/.pi/agent/ \
  /mnt/c/Users/slb/bench-orsmoke/ollama-bench/results/pi-agent-smoke/
```

The four bench commands, written into `run-smoke.sh` in the scratch clone and run from WSL
as `bash run-smoke.sh`. The bench is Windows-only and is driven through the Windows
interpreter over interop, no ssh and no pwsh.
`PY=/mnt/c/Users/slb/scoop/apps/python/current/python.exe`,
`AGENT='C:\Users\slb\bench-orsmoke\ollama-bench\results\pi-agent-smoke'` — the agent dir is
passed as a Windows path because the process that reads `PI_CODING_AGENT_DIR` is a Windows
process and cannot resolve `/mnt/c/...`.

```
PYTHONUTF8=1 "$PY" pibench.py --provider openrouter --models <id> --think medium --trials 1 \
  --no-tps --timeout 300 --tasks-dir results/v5/authoring/round2/suite-0 --num-ctx 24576 \
  --tag smoke-<short> --agent-dir "$AGENT" > "results/smoke-<short>.log" 2>&1
```

with the four `<id>`/`<short>` pairs `upstage/solar-pro4`/`solar`,
`inclusionai/ling-3.0-flash`/`ling`, `nvidia/nemotron-3-nano-30b-a3b`/`nemotron`,
`inception/mercury-2.5-preview`/`mercury`, all four launched together and `wait`ed on.
Key spend was read before and after with the `usage()` one-liner from `results/glm-v4.sh`
(`python3` in place of `python`, which does not exist on the WSL side).

## models.json registration

**None was needed.** All four ids were already present in the copied agent dir's
`models-store.json` (360 OpenRouter entries), each with `reasoning: true` and a context
window matching the brief: Solar 524288, Ling 262144, Nemotron 262144, Mercury 260000 (the
brief said 262144 for Mercury; the store says 260000). Each was probed first with a one-line
`pi -p` call from the scratch agent dir with `PI_CODING_AGENT_DIR` set to it and
`PI_OFFLINE=1`, and all four replied and exited 0, so `providers.openrouter.models` in the
copy's `models.json` was left untouched. `models.json` was therefore used exactly as copied:
the fleet routing (`zdr: true`, `data_collection: deny`, `sort: throughput`) applies to all
four models, and its `max_price` ceiling entries cover only `z-ai/glm-5.3-flash` and
`deepseek/deepseek-v4-flash-0731`.

**These four ran with no price ceiling.** That is acceptable for a smoke at these listed
prices — all four are at or below GLM's USD 0.075 input / 0.25 output per million: Solar
0.03/0.12, Ling 0.021/0.063, Nemotron 0.05/0.20, Mercury 0.04/0.15 — and the whole pass cost
USD 0.103941. It is stated here because a ceiling-free run is not the fleet's normal posture.

## Anything odd

- **Solar's g01 timeout.** The only task in the pass that did not finish. Killed at the 300 s
  cap with last stop reason `toolUse` after 3 turns and 16,525 output tokens — an unusually
  large output for so few turns. Its `usage_in` of 6,234 is the lowest cumulative input of any
  row in the pass, so it was not stuck reading; it was stuck generating.
- **Ling's provider errors.** Two rows carry errors, both transient and both on tasks that
  passed: g03 logged `Provider timed out after 13351ms` and then a 429, and t03 logged a 429
  reading `inclusionai/ling-3.0-flash is temporarily rate-limited upstream`. Worth confirming
  on a second run before treating Ling's 7/8 as repeatable.
- **Nemotron's token appetite.** 912,013 cumulative input tokens across 8 tasks against GLM's
  153,219 on the same tasks, and 98,630 output against 11,956. g03 alone is 517,986 input over
  44 turns. Its single-turn input peaks (20,439 / 20,361 / 21,053 on g01/g02/g03) are the
  highest in the pass but still inside the 24k band label.
- **Mercury's speed.** The whole 8-task arm finished in 46.4 s of summed task wall and 47 s of
  process wall — faster than GLM's 149.2 s by 3.2x, and faster than any other arm by an order
  of magnitude. Turn and tool counts are normal (45 turns, 54 tool calls), so this is not an
  arm that gave up early.
- **Bench code drift.** The scratch clone was taken at `6a491f5`; the campaign clone advanced
  to `dd1fb69` while the pass ran, which included `9560495` ("pibench extension hook") touching
  `pibench.py`. That change is purely additive and opt-in — it appends `PIBENCH_PI_ARGS` to the
  pi command line, and the variable was unset here — so the arm at `8efe111` is functionally
  identical to the tip for this run.
- **`--num-ctx 24576` is inert on this provider.** It is an Ollama-side setting and is ignored
  when `--provider openrouter` is used, exactly as the GLM baseline page notes.
