## Two corrections to the previous handoff, so you do not lose the time I did

- **There is no `D:\local-llm-bench\CLAUDE.md`.** It has never existed; there is no `AGENTS.md`
  either. The previous handoff tells you to read it as instructions before touching the repo, and
  you cannot. The repo's contract is `README.md` plus the plan.
- **You do not need `ssh fractal` or `sh -lc` to drive the GPU side.** Windows Python runs
  directly from WSL, with no ssh, no PowerShell, and none of the nested-quoting hazards the old
  page warns about:

      /mnt/c/Users/slb/scoop/apps/python/current/python.exe <script> ...

  run with cwd under `/mnt/d/...`, which that interpreter sees as `D:\...`. `nvidia-smi` also
  works directly from WSL. This is the invocation everything below assumes.

  One trap that follows from it, **corrected 2026-09-04 after the GPU owner reproduced both
  halves**: a Windows `ollama.exe` launched from WSL takes its cwd as a WSL UNC share, so a
  `/tmp/...` path resolves **only while the cwd is inside the WSL filesystem** and fails the
  moment the cwd is a Windows drive:

      cwd /tmp,                 -f /tmp/Modelfile   -> "success", exit 0, tag created
      cwd /mnt/d/local-llm-bench, -f /tmp/Modelfile -> "Error: no Modelfile or safetensors
                                                       files found", exit 1, no tag

  **The exit code is 1 and is trustworthy.** An earlier version of this page said it was 0 — "a
  failure that reports success" — and that was wrong. The mistake came from reading `$?` after a
  **pipeline**: `ollama create ... | tail -2; echo $?` reports `tail`'s status, which is 0 whatever
  ollama did. Use `${PIPESTATUS[0]}`, or do not pipe. Worth knowing generally, because the same
  mistake silently turns any failing command in a pipeline into an apparent success.

  The workaround stands: write the Modelfile into the `/mnt/d` tree and pass a **relative** path
  with the cwd set there. `make_grid_models.sh` does this and additionally verifies by reading the
  tag back, which is belt-and-braces rather than necessary.

  And: **a WSL-side `ollama serve` is running with zero models**, holding `127.0.0.1:11434` inside
  WSL. WSL-side Python hitting `localhost:11434` talks to *that* daemon and gets 404s that look
  like missing models. Windows-side Python correctly reaches the real Ollama. This cost me a
  confused diagnosis.

## What is done

- **KV-probe lifecycle faults: fixed and proven.** `kvquality.py` now has one `cleanup_barrier`
  replacing `kill_stray_servers`: process-tree kill via `taskkill /T /F`, a **bind** test on port
  18080 (deliberately without `SO_REUSEADDR`, which would let the test lie on Windows), **three
  consecutive** quiescent VRAM samples with reset on any bad sample, and a post-drain recheck for
  reappeared servers. It returns a structured reason, never a bare bool. Every exit path from
  `run_config` drains — health failure, normal completion, and an exception in the question loop —
  and a startup failure now carries the server log tail, so three indistinguishable "server did
  not become healthy" errors become three diagnosable ones. Proven with a live
  `--lifecycle-selftest` start/stop/start cycle **against a real allocation**:

      cycle 1  health_s 6.6  vram_peak_while_healthy_mib 14611  drain_observed true
               cleanup ok, waited 5.5 s, samples [1230, 1230, 1230]
      cycle 2  identical
      ok: true    drain_branch_proven: true

  A first attempt at this proof was worthless, and it is worth knowing why: it ran while the card
  happened to be idle, so every sample read the 1230 MiB baseline and the artifact could not
  distinguish "the drain waited for 14 GB to fall" from "there was nothing to drain". The selftest
  now records `vram_resident_samples_mib` and `vram_peak_while_healthy_mib` per cycle, and reports
  **`drain_branch_proven` as a field separate from `ok`** — `ok` says the cycle completed,
  `drain_branch_proven` says the run actually exercised the branch. Do not let those two collapse
  back into one field. And write `--out` to a per-run path: re-running over the same filename
  destroyed the earlier artifact that had the evidence in it.
- **The fifteen grid model tags: `make_grid_models.sh` builds them, and as of this handoff they
  are being built — do not assume they exist.** An earlier draft of this line claimed they did;
  that was false and the correction is at the end of this page. Why it matters more than it looks:
  pi passes no options, so `num_ctx` and `PARAMETER num_gpu 66` reach Ollama only through the tag,
  and a "48k cell" run against a base tag would silently run at 32768 without forced offload.
  The script itself had a second defect, fixed 2026-09-04: it drove its loop with
  `echo "$CELLS" | while read`, silently built only the first quant family — four of fifteen — and
  **exited 0**, twice in a row. It is now a flat loop and ends by counting the tags in `ollama list`
  and exiting non-zero unless all fifteen are present. Trust that count, not the loop's output.
- **The suite is authored: 8 tasks x 3 candidates = 24, all verified.** `verify_candidates.py`
  builds each candidate's sandbox exactly as `pibench.py` does and checks the reference passes
  (`SCORE m/m`, `PASS`, `VERDICT correct`) and that a did-nothing sandbox reads `visibly_failed`
  without crashing the grader. Final state: **REF 24/24, EMPTY 24/24, no problems.**
- **One candidate picked per task**, with reasons and a full section 4a audit record, in
  `authoring/selection.md`. Nothing was moved or deleted; all 24 remain.
- **Both gates are SATISFIED on all eight tasks.** Sonnet **3/3** and GLM **>=2/3** everywhere,
  which is plan rule 1 met in full. Two tasks were replaced on gate evidence along the way (g03
  and g04, both to `cand-1`); rule 1 provides for exactly that, and no quant evidence existed to
  contaminate the choice. Details and the reasoning: `findings-2026-09-04-gate.md` and
  `authoring/selection.md`.
- **`VERDICT correct|visibly_failed|confidently_wrong`** is now emitted by every checker, decided
  mechanically, which is what makes section 7's headline instrument computable without a human
  reading 120 grader tails.

## Unload Ollama before any direct-server run — the runner shares its name

`kvquality.py` launches its own `llama-server.exe`. **So does Ollama**: with a model resident,
`Win32_Process` shows a `llama-server.exe` whose parent is the Ollama server itself, and it
disappears when the model is unloaded. The cleanup barrier enumerates by image name and cannot
tell the two apart, so with a model loaded in Ollama it will burn its full 180 s and report
"VRAM did not reach three consecutive quiescent samples" — a correct refusal with a misleading
reason — and in the wrong ordering it would `taskkill /T /F` Ollama's runner, killing another
agent's work.

The harness docstring already requires Ollama to have nothing loaded, so this is a documented
precondition rather than a broken invariant; but it is one the code cannot check, and the failure
mode is killing someone else's model. **The fix, not applied:** identify candidates by parent pid
(`Win32_Process` returns `ParentProcessId` beside the pid) and refuse with the accurate reason
rather than killing. Until then, unload with `{"model": ..., "keep_alive": 0}` and confirm
`nvidia-smi` is near idle first — measured, the card went from 15,357 MiB to 1,230 MiB in about
two seconds.

## Two operational rules learned the hard way

- **Never dispatch a worker onto a tree another worker still holds.** Doing so cost two runs: a
  fix worker saw an authoring worker rewriting files underneath it, judged the tree unstable, and
  killed the other worker processes — destroying an authoring run, an in-flight gate run, and
  itself. `agent-run status` makes checking trivial.
- **A Codex worker has no permission system and full access, and will act drastically when its
  assumptions break.** Every brief for a worker on a shared tree should carry: *do not kill,
  terminate or signal any process you did not start; if something looks like it is changing under
  you, stop and report.* That line is in every brief dispatched after the incident, and the briefs
  are kept in `results/v5/briefs/` so they can be reused.
