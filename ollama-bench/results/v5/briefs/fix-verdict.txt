Task: fix a measurement defect in some of the v5 task checkers. Precise, mechanical, and there is
an acceptance command you must make pass. Work only in the repository you were started in.

THE DEFECT
Every v5 checker prints a line `VERDICT correct|visibly_failed|confidently_wrong`. That line is
the benchmark's headline instrument: `confidently_wrong` means the model produced fluent,
plausible, WRONG work, which is expensive because a human must catch it. `visibly_failed` means
the model crashed, refused, gave up, or produced nothing, which is cheap because it is obvious.

Several checkers decide the verdict with a rule of roughly this shape:

    verdict = "visibly_failed" if runtime_bad else "confidently_wrong"

where `runtime_bad` is set only when something raised an exception. That is wrong. It means a
model that DID NOTHING AT ALL -- never edited the file, gave up, ran out of time and produced no
change -- leaves the seed files exactly as they were, nothing raises, the pre-existing failure is
still there, and the checker reports `confidently_wrong`.

Consequence, and it is serious: in the real campaign a slow local model that gives up will be
counted as confidently wrong. The headline rate would be inflated by every non-attempt, which is
exactly backwards -- a non-attempt is the cheap, visible failure.

Confirmed today on g02/cand-1, g02/cand-2, g02/cand-3, g03/cand-1, g03/cand-2, g03/cand-3.
Do not assume that list is complete. The acceptance command below tells you the truth.

WHAT TO CHANGE
A checker must report `visibly_failed` when the model produced NO WORK. Concretely, at least:

- the required output artifact was never created; or
- the files the task asked the model to modify are byte-for-byte identical to the pristine seed;
  or
- the candidate module cannot be imported / does not parse; or
- the grader's own watchdog fired.

`confidently_wrong` is reserved for the case the instrument exists to catch: the model DID
produce work, that work is well-formed and runs, and it is wrong.

For the "unchanged from seed" test, embed the pristine content in the checker rather than reading
it from somewhere the model could have altered: compute a hash (hashlib.sha256 of the file bytes,
with newlines normalised so a CRLF/LF difference cannot cause a false "changed") of each seed file
the task asks the model to modify, and hard-code the expected digests in the checker. Include a
short comment saying why. If every such file still matches its pristine digest, the model did
nothing and the verdict is `visibly_failed`, whatever the tests say.

DO NOT DO THIS
- Do NOT weaken or remove the `confidently_wrong` detection to make the acceptance pass. Turning
  every failure into `visibly_failed` would make the acceptance command green and destroy the
  instrument. The two cases must stay genuinely distinguishable.
- Do NOT change `SCORE`, the total number of subchecks, `PASS`/`FAIL`, or the exit codes. Those
  are the existing contract and other things depend on them.
- Do NOT change any prompt.md, any seed/ file, any ref/ file, or the difficulty of any task.
- Do NOT touch pibench.py, the v4 tasks, or anything under results/ except as noted below.
- Standard library only. Deterministic. No network.
