## 0. The goal, restated

Push the **mean SCORE of the best local quant run down to about 0.50**, by keeping the v4 tasks
that still discriminate and adding tasks that look like the work the owner actually asks for:
Unity/VRChat avatar work. Secondarily: give the pi harness a fair shot at
tool-heavy work, accepting that this makes v5 **non-comparable to v4** (section 10).

Two numbers bound the design. Sonnet on v4 is at 0.968 mean / 13-of-21 pass — v4 is nearly
saturated for anything above Haiku. Haiku on v4 is 0.658 / 1-of-21. The 27B fp8 reference sits
between them. So v5 must add difficulty that is *tool-shaped* rather than *spec-shaped*: v4 proved
the 27B can write correct Python from a dense spec but loses on prose-only strictness; nothing in
v4 tests whether it can drive a stateful external application at all.

### The five findings that should be read before anything else

This section reflects a GLM audit of the plan and the nineteen fixes accepted from it

## 2. What the 27B quants demonstrably can and cannot do, from v4

Evidence: `results/v4-authoring/report.md`, `results/sonnet-v4/report.md`,
`results/v4-local-medium.{json,log}`, `results/v4-ref-medium-1800.{json,md}`,
`results/plan-2026-09-03.md`.

**Can:**
- Write substantial correct code from a dense spec. fp8 medium scored 0.93-1.00 on eight of the
  round-1 v4 tasks (shell quoting, CSV dialects, path normalization, money/decimal, date
  arithmetic, version comparison, NULL aggregation) — all rejected as saturated.
- Run a long agentic loop. The fp8 reference averages **34.2 tool calls per run** and 53,702
  output tokens per run at 1800 s over 6 runs, 3/6 passing, mean 0.89
  (`results/v4-ref-medium-1800.md`, snapshot 2026-09-03 11:25 — **that campaign is still in
  flight and these numbers will move**; an earlier draft of this plan quoted 55.3/68k from a
  snapshot the run has since overwritten, which is exactly the "scores rot" failure the skill
  warns about). Tool use per se is not the problem at fp8.
- Self-test and iterate: the v4 authoring report's central finding is that anything a competent
  developer would think to test gets fixed by the model itself.

**Cannot:**
- Un-self-testable strictness. Error *kinds*, error *precedence* between phases, exact byte
  offsets on malformed input, canonical output forms, sign/rounding on ties. This is the *only*
  place fp8 and Sonnet both still lose checks (Sonnet loses one or two; Haiku loses ten).
- Honour bans reliably (importing a forbidden module was a repeated v2 failure).
- **Largely unmeasured on the local ladder, because the harness capped it.** Over the 13 Q2_K_L
  rows recorded so far: **zero passes, but mean SCORE about 0.068, not 0**. Nine rows are the
  one-turn / zero-tool-call signature, but **three are not** — `55_minilang t0` (2 turns, 1 tool
  call, 0.1935), `57_stateful t0` (**5 turns, 1 tool call, 0.6154**) and `57_stateful t1` (3
  turns, 0.0769). So the quant demonstrably *can* reach a tool call and earn substantial partial
  credit. **Section 7a shows the zeros are pi handing the model the entire residual 32k window as
  its output allowance**: predicted `max_tokens` matches observed `out_tokens` at delta 0, +34,
  -20 and -14 across four tasks. Until H1/H2 in section 7d are applied, the local arm of v4
  measures the harness **on the tasks where the quant never escapes turn one** — which is most of
  them, but not all, and `57_stateful` is the standing counterexample. Q3_K_S/Q3_K_M are still in
  flight.

**What that means for v5 task design:**

1. **A Unity task with the *full* 48-tool schema set cannot run locally at 32k.** With all Unity
   schemas loaded (~21.5k tokens of a 32k window) plus a repo context file, pi requests
   `max_tokens: 1` and the run is over before the first token (7b, scenario A). But the
   **core-subset** case is tight and viable: 29 tools leaves ~9.7k of response (scenario D), and
   the bench gateway is *already* a pre-model tool-list rewriter — it hides seven tools and makes a
   startup call at `gateway.py:441`, so pre-calling `manage_tools` there delivers the subset
   without the model ever seeing the fat schemas. **So 64k is strongly recommended for headroom,
   not a hard prerequisite** (question Q7). Pure-file tasks are comfortable at 32k. **Note the
   arm that was comfortable at 32k regardless — Blender — is the one that has been dropped**, so
   at 32k the whole non-trivial half of v5 now rests on the Unity tool subset working.
2. Unity tasks are *automatically* un-self-testable in the v4 sense: the model cannot
   check its own answer without measuring, and the grader re-measures independently. That is
   exactly the failure surface v4 identified — v5 gets it for free instead of having to author
   prose-only strictness into every spec.
3. **Prompt and tool-schema budget is a first-class design constraint, and it is now measured.**
   A v4 prompt is 12.7-19.2 KB with no tool schemas at all (pibench runs pi with
   `--no-extensions --no-skills --no-context-files`). A Unity task adds 86 KB of Unity tool
   schemas, the contestant `CLAUDE.md` and the skill copy. **Keep every v5 prompt short.** At 32k
   each kilobyte of prompt costs a quarter-kilotoken of the model's entire thinking-and-answering
   allowance; the v4 prompts were long only because nothing was competing for the window.
4. Keep partial credit fine-grained. Eight-plus independently weighted checks per task is what
   turns "the model failed" into a number between 0 and 1; with a suite aiming at a 0.50 mean, a
   pass/fail suite would just read 0.

## 4. Candidate tasks

Each entry: **fixture** (what is planted) / **grader** (what the hidden checks verify) / **SCORE**
(partial-credit weights) / **difficulty** / **surface** (Unity or pure-file).

**These are sketches, not specifications.** Every weight set below sums to 1.0 and every one is
deliberately coarse (4-7 checks). The difficulty predictions are guesses; the Haiku and Sonnet
gates, not this table, decide what ships. Expect a third of these to be dropped or merged during
authoring.

Three authoring rules apply to every one of them, and each exists because something already went
wrong once:

1. **Meet the section 3 floor before the gates, not after.** >= 5 checks and <= 0.35 on any single
   check; >= 8 checks for a `build` task. Several sketches below currently miss this and must be
   split during authoring — U4, B2 and P3 each carry a 0.35 check, and only U7 has eight.
2. **`_selfcheck.py` must flip each check individually**, on a hand-built wrong solve, not merely
   flip the task as a whole. A check that cannot be made to fail on demand is not a measurement —
   it is a check every model will pass or every model will fail, which is the grader-bug class that
   has already cost this suite twice. Any check that will not flip is demoted to a report or
   honesty check.

### 4a. The trap catalogue — what the hidden graders should actually check

A benchmark task is only worth running if it turns on something that **fails silently**. Mining
`D:\avatars` (git log to 600 commits, `docs/`, the ten `vrchat-avatars` reference files, the
`com.slb.avatar-tools` README, `cut_journal`) produced ~50 such traps. These are the ones with the
best ratio of "no error message" to "programmatically checkable"; each one is a candidate hidden
check, and several of the tasks above are built directly on them.

**Ordered arrays with no names (the nastiest class in the pipeline)**
1. `m_Bones` and `m_BlendShapeWeights` are index-keyed and carry no names. Reordering imports with
   no error and misaligns them. Real casualty: `B_shape_legs_claws` was silently zeroed and the
   avatar **shipped clawless** (`crispy/CLAUDE.md:108-115`). -> U7.
2. VRCFury `BlendShapeLink` binds by **name** with `exactMatch: false`; renaming or dropping a
   shape breaks the link with no warning. -> U7.
3. Blender appends `.001` to a remade shape key, object or material slot. New name = new fileID =
   null reference, no warning. Still worth a **Unity-side** check on any task that imports an FBX,
   even though the Blender arm is gone.
4. PC and Android synced-parameter lists that disagree in name, type, order or sync flag: a remote
   client decodes the other bundle's list. No error anywhere. -> a strong candidate for a 14th
   task; gradeable by capturing both built `VRCExpressionParameters` and comparing element-wise.

**Measurement (all of these make a confident wrong answer look right)**
5. **VRChat counts disabled renderers.** Toggling a prop off changes the measured numbers by
   exactly nothing; only deleting does, which is what `Cost Of Selection` does on a throwaway
   clone. -> U2.
6. Pre-build stats are not upload stats. An avatar reading VeryPoor in the open scene can ship
   Medium. -> every measure task; already the honesty surface in `builds-worse`.
7. The SDK's `materialCount` deduplicates shared materials; the website charges the **raw slot
   sum**. Baked SPS sockets make the gap real. -> `material-slots`, already in the suite.
8. A `Standalone` platform override with `overridden: 1` silently wins; editing the Default tab
   changes only the Android build. Top-level `maxTextureSize` is the legacy field. ->
   `texture-budget`, already in the suite.
9. **The atlas overrides `maxTextureSize` in the expensive direction**: a tile is sized from the
   *imported* texture but a page is resampled from the *native file*. -> U3.
10. `isReadable: 0` in a `.meta` forces VeryPoor **by itself**, regardless of triangles. -> a
    one-line plant that no amount of polygon counting will explain; excellent distractor.
11. In batch mode ratings stay `null` until `CalculateAllPerformanceRatings()` is called, and
    parsing `AvatarPerformanceStatLevels_*` alone yields `None` (the levels are referenced by
    GUID) so everything grades VeryPoor. -> a grader-integrity hazard, not a task.

**Shaders and locking**
12. Locking bakes non-animated properties to constants: the slider still moves, the animator still
    writes, and there is **zero visual change**. The fix is the `_X_Animated: 1` tag, then relock.
    -> U9.
13. `Unlock()` deletes sibling `<Material>-*` folders it judges unused, including the one a
    committed material *variant* points at. Unrecoverable. -> U9, scored as a forbidden action.
14. Lock state reaches the `.mat` only on File > Save Project; until then git shows a torn state
    that is not corruption.
15. Fast Fur `_ScaleCalibration` derives from one vertex's baked normal magnitude; any topology
    change reindexes it, and the guard is `if (_ScaleCalibration < 0)` so it never self-heals. It
    reads as "the fur shader stopped working". Sibling fur materials on one mesh must agree - the
    outlier is the bug, and that is a one-line grep check.
16. Every Mochie property named "Roughness" holds **smoothness**.

**Build pipeline**
17. Every animator layer after index 0 is created at weight 0 - the commonest "wired it up and
    nothing happens".
18. A VRCFury `[SerializeReference]` action list edited on a prefab *instance* (and a variant **is**
    an instance) reads back perfectly in-session and is gone after the next reload. -> U8,
    `toggle-default-on`.
19. `PrefabUtility.SetPropertyModifications` reverts every override Unity was not told about;
    `RecordPrefabInstancePropertyModifications` must come first. This lost three material swaps
    and a body albedo once.
20. d4rk's `ignoreTransforms` means "stop descending", not "skip". A PhysBone root inside its own
    list makes every child non-moving and `DeleteUnusedGameObjects` bakes them away -
    "everything is there but nothing moves". -> U6.
21. A prefab variant can `m_RemovedComponents` an inherited optimizer and add a fresh one with all
    merges off, silently reverting a tuned config. -> U6, U8.
22. VRCFury bakes an SPS marker renderer under every socket regardless of `m_IsActive`, so a bad
    socket blows the AABB only *after* build. -> `builds-worse`, already in the suite.
23. VRCFury logs ordinary build progress with `type: "Exception"`, so scanning for exceptions is
    pure false alarms. -> a grader-integrity hazard.
24. `SkinnedMeshRenderer.localBounds` is in root-bone space and is reset by assigning
    `sharedMesh`; a wrong one frustum-culls the renderer, which looks exactly like a mesh that
    failed to load.

**FBX and assets**
25. `optimizeGameObjects: 1` strips and reorders bones. -> P2.
26. Applying object transforms before export moves the root conversion onto the Unity node - fur
    ends up 100x too thick with nothing else visibly wrong.
27. Exporting mesh-only (armature not selected) strips skin clusters; the garment lies sideways at
    the origin.
28. `shape_key_add()` creates at 1.0 and ships as `DeformPercent` 100. (Reachable from Unity as an imported weight, now that the Blender arm is gone.)
29. Never delete an FBX's `.meta` or move the FBX: GUIDs are path-keyed, per-object fileIDs are
    name-keyed, and both orphan every reference. -> P2.

**git and repo**
30. A missing `git lfs install` silently commits raw blobs; a new `.gitattributes` pattern fixes
    only *future* commits, and ignore rules are inert on already-tracked paths. -> P1.
31. Per-project `.gitignore` files ignore `*.unitypackage`, so a purchase dropped into a Unity
    project folder never appears in `git status` and is never backed up.

**Tooling hazards for whoever writes the graders**
32. Parsing Unity YAML in Python: `m_GameObject: {fileID: 0}` is a **truthy dict**; a naive falsy
    check drops every ScriptableObject - which is all VRCFury config, every menu and the
    parameters asset.
33. `.anim`/`.controller` `genericBindings` `path`/`attribute` are `zlib.crc32(s) & 0xffffffff`.
    YAML that parses clean is not verified.
34. `EditorUtility.RequestScriptReload()` does **not** reload over the MCP bridge; a real domain
    reload needs a throwaway script compiled into the project (which is exactly what
    `toggle-default-on`'s grader does).
35. `UnityMCP.execute_code` is **CodeDom C# 6 only** - no string interpolation, no local
    functions, no `using`, fully-qualified type names.
36. Async shader compilation renders solid cyan, and a screenshot taken straight after a state
    change can return the previous frame. Never grade from a screenshot.
37. d4rk's *Optimize in Play Mode* defaults on, so play-mode tooling enumerates the optimized
    clone, not the avatar.
38. Fast Fur's grooming tool disables every PhysBone on entering play mode, and logs nothing.
39. Build & Test **mints** a blueprint id into any blank PipelineManager - often onto the *scene*
    instance, which a prefab-only check misses. `Build` and `BuildAndUpload` save the open scene.
    -> the `blueprint_minted` forbidden check already in three graders; keep it in every v5 task.
40. An *untitled* throwaway scene turns the SDK's pre-build save into a modal dialog that freezes
    the editor with no error. -> a fixture must never leave an untitled scene active.

**Two things that are NOT gradeable, and must not be turned into checks:** which bone a VRChat
client actually grabs (the editor cannot measure it), and whether a texture or a fit "looks
right" - clipping acceptance is an owner ruling, not a measurement. Tasks that touch these must
grade the *honest statement of the limit* instead, which is what U5 does.

## 5. The validation campaign

The owner's two gates, applied to every candidate before any local or OpenRouter money is spent:

1. **Haiku gate (is it hard enough?)** — 3 trials. **3/3 pass, or mean SCORE > 0.95 => too easy**,
   revise and re-probe. At least one Haiku failure is required to proceed.
2. **Sonnet feasibility (is it still achievable?)** — 3 trials. **>= 1 pass in 3, or mean >= 0.85
   => achievable**, proceed. **0/3 with mean < 0.85 => suspect the task** (ambiguous prose,
   over-strict or buggy grader) before blaming the model.

**A conflict in these two rules, surfaced by the GLM audit and worth resolving before the first
gate rather than at it.** The Sonnet rule will bounce exactly the tasks the suite most needs to
reach a 0.50 local mean — U3 (predicted Sonnet 0.4-0.7), and plausibly U6, U9 and B3 — while
section 8's "score too high" remedy assumes those same tasks are available to admit. Symmetrically,
the Haiku rule passes a near-saturated task: 2/3 passes at mean 0.94 clears it. So the two gates as
written can reject a good hard task and accept a weak easy one.

**The waiver lane — ANSWERED 2026-09-03, Q10 = A: hard tasks are authored and gated, and the waiver lane is adopted exactly as specified below.** (`decimate-under-budget` stays dropped, with Blender.) A task is admissible despite Sonnet 0/3 if all three of
(a) its `_selfcheck.py` golden solve scores >= 0.95, (b) every check flips individually on a
hand-built wrong solve, and (c) Haiku mean < 0.30. Such a task is recorded as **"hard, waived"**
and reported separately, so it can never quietly inflate a difficulty claim. The point of the
Sonnet gate is to catch *ambiguous prose and buggy graders*; (a) and (b) test for those directly,
which is what the gate was proxying for.

Both cost **zero OpenRouter spend**; the cost is Anthropic plan usage, which is what the USD
figures below estimate.

**But the two gates are not run the same way for the two kinds of task, and this matters for
containment.**

- **Pure-file candidates** are gated exactly as v4 did it: Claude Code
  subagents on `haiku` / `sonnet` working in a copied sandbox, graded by the task's own hidden
  test. The runners already exist at `results/haiku-v4/` and `results/sonnet-v4/run.py`; reuse
  them. Cheap, parallel, no editor.
- **Unity candidates are gated through the VRCA-Bench runner** — **owner ruling 2026-09-03, Q12 =
  A** — i.e. `runner run --tasks <id> --models haiku,sonnet --trials 3 --effort high
  --editors A,B,C`, which launches `claude -p` contestants behind the gateway. **A free-form Claude
  Code subagent must never drive a bench editor for a recorded gate.** A subagent reaching the 8080 hub is not pinned to
  one instance, is not screened by `policy.json`, is not logged to `gateway.jsonl`, and is not
  covered by the contestant deny list — it would be a containment regression *and* it would not be
  measuring the same thing the scored runs measure. The runner's per-run reset from `golden/` is
  also what makes the three trials independent.

That is why the Unity gate cost in 5c is priced at the recorded `claude -p` contestant rates
rather than at subagent rates.

### 5a. Order of operations per candidate

```
author task dir  ->  _selfcheck.py (golden >= 0.95, no-op <= 0.35, trap flips its own check)
                 ->  Haiku gate x3   ->  revise until it fails at least once
                 ->  Sonnet feasibility x3  ->  revise until achievable
                 ->  admitted to the v5 suite
```

A task that has not passed `_selfcheck.py` never reaches a gate. This is non-negotiable: the
suite has already been bitten twice by graders that every model failed identically.

### 5a1. Mandatory instrumentation at every batch boundary (owner ruling, 2026-09-03)

**There is no plan-usage cap.** The owner chose that deliberately, with live numbers in front of

### What is missing, and the smallest bench-local mechanisms that would close it

Five gaps. None is a prompt rule; all are code, all bench-local, and M1 and M3 are a few lines each.

**M3 — containment checks on the three functions that take a path (closes rows 1 and 2). Highest
priority: it is the only gap with a destructive failure mode.** Three sites accept an arbitrary
path or slot and route into a `robocopy /MIR`:

1. `projects.reset_assets(project_dir_path)` — assert the resolved target is under `paths.PROJECTS`
   before building the command. Two lines, and it is the one that deletes files.
2. `projects.launch_editor(project_dir_path)` — same assertion, so `reuse=True` can never hand back
   a foreign editor's PID.
3. `runner.project_dir_for(editor)` — call `projects.project_dir(editor)` instead of formatting the
   path by hand, and validate `--editors` against `BENCH_SLOTS` at parse time (`runner.py:1460`) so
   a typo fails at argument parsing rather than inside a mirror.

Nothing triggers these automatically today — the runner never launches editors and only ever passes
`project_dir_for(editor)` — so this is a latent hazard, not a live one. But agents are the intended
callers of `bench/projects.py`, which makes "an agent calls it with the wrong path" the ordinary
case rather than a remote one, and the cost of the check is trivial next to the cost of the failure.

**M1 — a RAM floor before a batch, and between runs (closes row 6).** `free_memory_gb()` already
exists and is already the right function; it is simply never called. The minimal change is a
pre-flight assertion in `cmd_run` plus a check as each worker takes an editor from the pool: refuse
to start, or park the worker, when free RAM is below a floor (8 GB is the figure the existing
GPU watchdog already uses). Worth adding to the same pre-flight: **warn when a non-bench Unity
instance is connected to the hub**, which is the cheap signal that the owner is at his desk.
Cost: a few lines in `bench/runner.py`. **This is the highest-value isolation change that addresses
a live risk**, because it is the only contention point where a batch can damage the owner's session
today without anyone making a mistake.

**M4 — extend `policy.json` to `EditorPrefs`, and stop trusting it for paths (closes row 8, partly).**
Add `EditorPrefs`, `MCPForUnity.` and `EditorApplication.OpenProject` to the screened patterns.
Note the honest limit: `policy.json` is literal-regex screening of `execute_code` source text, so a
determined evasion by string concatenation defeats it — it is a guard against accident, not against
intent. The structural containment of row 1 (once M3 lands) is what actually holds; `policy.json`
should be described that way in the plan rather than as a boundary.

**M5 — one test pinning the session-scoping of `set_active_instance` and `manage_tools`.** Rows 4
and 5 are both hard guarantees today, and both rest on an implementation detail of a pinned
third-party version (`mcpforunityserver 10.1.2`, FastMCP's session-prefixed state store). The
existing tests use a fake server (`tests/test_unitymcp.py:143`), so a regression to the pre-#1023
`client_id` keying would pass the suite silently and re-point the owner's live session. One
integration check against a live hub, run at upgrade time rather than per batch, is enough.

**M2 — `manage_tools` scope: settled, and now a constraint rather than a probe.** The wire probe
proposed on 2026-09-03 has been superseded by reading the vendor source (row 5): activate,
deactivate and reset are session-scoped. **M2 is therefore reduced to a single rule: the gateway
must never call `action: "sync"`.** That belongs in the H10 implementation as a comment and, better,
as an assertion.

**A sixth item that is not isolation but is adjacent (row 7):** the console is not cleared between
runs, so a batch should not follow interactive scratch work on the same editor. That is a batch
hygiene rule, and it is already recorded as risk R3.

### The guarantee I can and cannot give

**Can give, and it is narrower than the first draft of this section claimed:** *the automated batch
path* cannot open, lock, reuse, re-point or write to the owner's `fargo-crispy` project or editor.
The runner never launches an editor, and every path it does take is composed from a constant root
and a slot whitelist. Rows 3, 4 and 5 hold structurally and unconditionally: instance routing is
pinned per call and cannot be moved by a contestant, `set_active_instance` is keyed by an
`mcp-session-id` the owner's client does not share, and `manage_tools` visibility is session-scoped.
Q12 = A keeps every contestant call inside that gateway.

**Cannot give, three things.** First, **the module API is not contained** — `reset_assets`,
`launch_editor` and `project_dir_for` accept any path, and one of them mirrors with `/MIR`, so an
operator typo or a mis-called helper can delete the owner's `Assets/`. Until M3 lands, "a bench run
cannot touch your project" is true of the runner and **false of the library the agents call.**
Second, no guarantee that a batch does not **contend for the machine**: port 8080 is shared by
design (row 3), and there is **no RAM guard whatsoever** (row 6). Third, `EditorPrefs` is a
machine-global writable surface reachable through `execute_code` (row 8).

The honest one-line statement to the owner is therefore: *"a batch cannot reach your project by
accident of design, but it can reach it by accident of typing, and it can starve your machine
either way."* **M3 and M1 together change that sentence, and both are small. Neither blocks task
authoring; both should land before the first gate batch.**

**Does anything beyond Q12 = A need to change? Yes, two things.** Q12 = A governs *contestant*
calls, and that is the largest share — but two other paths reach the hub and are **not**
gateway-pinned: (i) the **harness itself** — fixtures and graders call `ctx.mcp` directly, and
`bench/unitymcp.py` passes `unity_instance` explicitly per call, so those are pinned by argument
rather than by the gateway; that is sound but it is a different mechanism, and any new fixture must
keep passing it; (ii) **my own authoring and `_selfcheck` work**, which drives one named editor
directly and is the one place a human-driven mistake could reach the wrong instance. For (ii) the
discipline is that `_selfcheck.py` already takes the slot as `sys.argv[1]` and must always be given
one explicitly, never left on its `"C"` default while another editor is in play.

## 7. The pi harness for tool-heavy work

**This section contains the most important finding in the plan. The Q2_K_L "runaway thinking"
failure is not a model defect. It is arithmetic in the pi harness, and it makes Unity MCP work
impossible for any 32k local model at any thinking level.**

### 7a. The mechanism, verified

`clampMaxTokensToContext` in
`~\scoop\persist\nodejs-lts\bin\node_modules\@earendil-works\pi-coding-agent\node_modules\@earendil-works\pi-ai\dist\api\simple-options.js`,
verbatim:

```js
const CONTEXT_SAFETY_TOKENS = 4096;
const MIN_MAX_TOKENS = 1;
export function clampMaxTokensToContext(model, context, maxTokens) {
    if (model.contextWindow <= 0) return Math.max(MIN_MAX_TOKENS, maxTokens);
    const available = model.contextWindow - estimateContextTokens(context).tokens - CONTEXT_SAFETY_TOKENS;
    return Math.min(maxTokens, Math.max(MIN_MAX_TOKENS, available));
}
```

`estimateContextTokens` counts the system prompt **and the tool schemas**, at 4 chars per token.
Since `pi-agent/models.json` pins `maxTokens: 32768` equal to `contextWindow`, the `Math.min` never
binds: **pi hands the model the entire residual window as its output allowance.** Reasoning and
answer share that allowance — pi's own source says so at
`pi-ai\dist\api\openai-completions.js:735-738`: *"Reasoning and the answer share max_tokens here, so
an uncapped reasoning phase can consume the whole response and leave no answer and no tool call."*
The cap that would prevent it, `compat.thinkingTokenBudgetField`, is **off by default and not set in
`pi-agent/models.json`**. Note the same file also exports `MIN_ANSWER_TOKENS = 1024` and
`clampThinkingBudgetToAnswerRoom`: **upstream already contains the shape of the H3 fix**, which is
a good sign for H3 even though Ollama may not honour the wire field.

**Independently verified by this session** against `results/v4-local-medium.json`. Predicting
`max_tokens = 32768 - ceil(len(prompt.md)/4) - 1339 - 4096`, where 1339 is the measured system
prompt (660) plus four built-in tool schemas (679):

| task | prompt.md bytes | predicted `max_tokens` | observed `out_tokens` | delta |
|---|---|---|---|---|
| `52_reengine` (3 trials) | 12,725 | 24,151 | 24,151 | **0** |
| `55_minilang` (2 one-turn trials) | 14,348 | 23,746 | 23,780 | +34 |
| `56_tmpl` (3 trials) | 19,199 | 22,533 | 22,513 | -20 |
| `59_uri` (trial 0, landed later the same morning) | 10,214 | 24,779 | 24,765 | -14 |

The last row was predicted *before* that run landed and checked afterwards, on a task the quant
had not yet been run on at this config — so the relationship is **predictive, not fitted**.

The model is not failing to stop. It is spending exactly the allowance it was given, on reasoning,
and hitting `stopReason: "length"` with no text and no tool call. Two compounding faults hide it:

- **pi's own recovery is switched off by the bench config.** `agent-session.js:1628-1690` would
  detect a recoverable `length` stop and compact-and-retry the turn — but line 1630 returns
  immediately because `pi-agent/settings.json` sets `"compaction": {"enabled": false}`.
- **pibench cannot see the failure.** `run_pi` records an error only when
  `stopReason == "error"`. pi's stop reasons are `stop | toolUse | length | error | aborted |
  deferred | pending`; **`length` is invisible**, so the run records `rc=0`, no error, and a bare
  zero score.

**Owner decision, 2026-09-03: the v4 ranking runs to completion unchanged, and is not re-run.**
This finding is kept as a **standalone finding**, not as a reason to restart eight hours of GPU
work. The consequence is a reporting obligation rather than a scheduling one: every v4 local number
carries a **harness-cap caveat** reading, in substance, *"measured at num_ctx 32768 with
`maxTokens` equal to the context window, so pi granted the model the entire residual window as one
response allowance; scores at this configuration are a lower bound on the quant and partly measure
the harness."* Do not report the Q2_K_L zeros as a quant capability finding without it, and do not
quietly compare a v4 local number against any v5 local number taken after H1/H2 land.

**The signature is not uniform, and the later tasks confirm the same ceiling from a different
angle.** As the ranking progressed past the first three tasks, `57_stateful` produced
`turns=5 tools=1 out=22748`, `turns=3 tools=1 out=22760` and `turns=0 tools=0 out=0`, the first
two carrying `ERR=Stream ended without finish_reason`. So the quant *can* reach a tool call - it
is not incapable — but the cumulative output still lands within about 4% of the same predicted
ceiling before the stream dies. That is the identical budget problem surfacing as a transport error instead of a
clean `length` stop, and it is a second reason the harness cannot currently tell a model failure
from an allowance failure (H4).

### 7c. The other out-of-the-box failure modes

1. **No turn cap exists.** Grepping `maxSteps|maxTurns|maxIterations|stepLimit` across
   `pi-coding-agent/dist` returns zero hits; the loop is `while (true)` at
   `pi-agent-core/dist/agent-loop.js:85`. The only lever is the extension hook
   `shouldStopAfterTurn`, not reachable from the CLI or settings. `task.max_turns` is inert.
2. **A live spin risk.** At `agent-loop.js:133-138,272,280` a `length` stop *with* tool calls fails
   every call ("arguments may be truncated") but returns `terminate: false`, so `hasMoreToolCalls`
   stays true and the loop retries with nothing to break the cycle. A 27B that over-thinks past
   `max_tokens` while emitting tool calls will spin until the external timeout.
3. **The managed `reserveTokens` is fatal on any 32k model.** `~/.pi/agent/settings.json` sets
   `compaction.reserveTokens: 548576`, sized for GLM 5.3 Flash's 1M window. The trigger is
   `contextTokens > contextWindow - reserveTokens`, i.e. `> -515,808` on a 32k model — **true on
   every turn**. `ansible-slb/group_vars/all/vars.yml:439-441` predicts this in writing. Never
   point a local model at the managed agent dir.
4. **`--tools` is a trap.** It is a strict allowlist over *all* tools, so naming built-ins silently
   strips every `mcp_*` tool. `--exclude-tools` / `-xt` is the denylist that works.
   `pi-mcp-extension@1.5.0` has **no** tool filter of its own — its entire settings surface is
   `{toolPrefix, requestTimeoutMs, maxRetries}` and `listAllTools` pages to exhaustion and
   registers everything.
5. **Schema fidelity is silently degraded.** `tool-bridge.ts::convertJsonSchemaToTypebox` drops
   `default`, `title`, `format`, `minimum`/`maximum`, `minLength`/`pattern`, `examples`, `const`
   and non-string `enum`s; `integer` collapses to `Type.Number`; anything untyped or nested past
   depth 10 becomes `Type.Any()`. The extension also never reads the server's `instructions`, so
   Unity's ~5 KB instructions block **never reaches a pi model at all** — a Claude Code contestant
   gets guidance a pi contestant does not.
6. **Resources are not bridged**, so `mcpforunity://…` is unreachable and the same information must
   come from a tool call.
7. **pi cannot choose its Unity editor** (`additionalProperties: false`), which is why the bench
   gateway injects `unity_instance`. Never let pi call `set_active_instance` — it is machine-wide
   state that would move whichever editor another agent is driving.
8. **pi exits 0 in `--mode json` even when the model call failed.** Read the transcript, never the
   exit code.

### 7f. The nesting guard, and why the bench path needs its own

Another agent is adding an `AGENT_RUN_DEPTH` env marker to the `pi-run` and `codex-run` wrappers in
ansible-slb, so that a nested wrapper call is refused. **The bench contestant path does not go
through those wrappers** — `bench/contestants.py` launches `pi` directly, and `runner.py` launches
`claude -p` directly — so the question is whether the fleet guard covers a bench contestant. It
does not, and the reason is a deliberate design decision that now points the wrong way.

**What the code does today (verified at source):**

- `runner.contestant_env` (`runner.py:962`) is `dict(os.environ)` minus `ENV_STRIP`, plus
  `VRCA_BENCH_RUN_ID`. `ENV_STRIP` (`:120-127`) removes `ANTHROPIC_API_KEY`,
  `ANTHROPIC_AUTH_TOKEN`, `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SSE_PORT` and
  `CLAUDE_CODE_SESSION_ID`, with the comment: *"parent-session markers that make the child think it
  is nested inside another Claude Code run"*.
- `contestants.pi_env` (`contestants.py:636`) starts from `dict(base_env)`, removes every
  `*_API_KEY`/`*_API_TOKEN` except `OPENROUTER_API_KEY`, and adds `VRCA_BENCH_GUARD_CONFIG`,
  `PI_OFFLINE`, `PI_SKIP_VERSION_CHECK`.
- `AGENT_RUN_DEPTH` appears in neither list, so it is **inherited if set and absent if not**.
- The contestant deny list is 43 entries and **none of them mentions `pi`, `codex`, `claude`,
  `node`, `npm`, `agent`, `curl` or `http`** (verified by scanning
  `bench/contestant/settings.json`). `guard.ts` screens forbidden *paths*, not commands.

**The consequence, which is a genuine conflict of intent.** The bench strips nesting markers *on
purpose*, so that a contestant behaves like a fresh top-level session and two runs of the same
model do not differ by how the batch happened to be launched. The fleet guard wants the opposite: a
marker *present*, so a nested call is refused. Today that produces two bad outcomes depending on
nothing but the launching shell:

- Batch launched from a session that already has `AGENT_RUN_DEPTH` set: contestants inherit it, a
  nested `pi-run` is refused — but the benchmark environment now varies with how it was started,
  which is exactly what `ENV_STRIP` exists to prevent.
- Batch launched from a clean detached shell (the normal case): no marker, and **a contestant that
  runs `pi-run` or `codex-run` spawns a nested agent that bills the OpenRouter account or the
  ChatGPT plan, outside the guard and outside the benchmark's cost accounting.** Nothing in the
  deny list stops it, and a pi contestant has no permission system at all.

**Answer to the question asked: yes, the bench path needs its own equivalent guard, and it must be
explicit rather than inherited.** The minimal bench-local change is two lines:

1. Add `AGENT_RUN_DEPTH` to `ENV_STRIP`, so an inherited value can never make one run differ from
   its siblings; and
2. **set** it explicitly in `contestant_env` (and therefore in `pi_env`, which builds on it) to the
   value the wrappers treat as "already inside an agent".

That gets both properties at once: the environment is identical for every run regardless of how the
batch was launched (benchmark fidelity), and the marker is always present, so a nested `pi-run` or
`codex-run` is always refused (containment). It also costs nothing in the record, and it should
land before the first gate batch rather than after.

**Do not assume the ansible-slb work covers this.** It covers the wrappers; the bench does not use
them.

## 10. Why v5 is not comparable to v4, and how to report it

Every one of these alone breaks comparability; v5 has all of them.

1. **Different task suite.** Only two of seven v4 tasks survive; twelve to sixteen are new. v5 is
   Unity plus pure-file; there is no Blender arm (dropped by the owner 2026-09-03), so v5 also does
   not measure the mesh-work dimension it was originally scoped to cover — say that in the report
   rather than letting "Unity and Blender" survive in the framing.
2. **Different harness.** v4 ran pi with `--no-extensions --no-skills --no-context-files` — no MCP
   tools, no skill, no context files. v5 loads MCP tools, a bench `AGENTS.md`, and for Unity tasks
   a contestant profile. That is a different agent.
3. **Different pi configuration** (H1-H12: a `maxTokens` cap, compaction re-enabled, a thinking
   budget if Ollama honours one, `stopReason` recording, tool subsetting, an appended system
   prompt).
4. **A different serving config** (64k / q4_0 / num_gpu 66 - question Q7), which for the Unity arm
   is not optional.
5. **The v4 local numbers are themselves partly harness artefacts** (section 7a). So v5 is not
   just non-comparable to v4 - part of v4's local arm should be *reissued with a footnote* rather
   than compared against at all. The honest statement is that v4 measured the pure-file suite at
   fp8 well and measured the local quants at a configuration that capped them.
6. **Different scoring surface.** v4 SCORE is a fraction of randomized differential cases; v5
   SCORE is a weighted sum of programmatic checks minus forbidden and honesty penalties. The two
   numbers are both in [0,1] and mean different things.
7. **Different failure mode in the denominator.** A v4 zero means "wrong code"; a v5 zero can mean
   "never reached a tool call", which is a harness-and-model interaction, not a coding result.

**Reporting rule:** the v5 report carries its own table and states, in the first paragraph, that
no v5 number may be compared to any v4 number. Where a trend is genuinely wanted, the only honest
bridge is the two retained pure-file tasks (`52_reengine`, `56_tmpl`) **run under the v5 harness
config** — and even those must be labelled "same task, different harness". The v4 ladder stands on
its own as the last measurement of the pure-file suite; it is not superseded, it is a different
experiment.

## Authoring rule: prompt length (drafted 13:50, CONFIRMED by the owner 13:58, 2026-09-03)

Owner observation: "In trying to write harder tests, many of these tests are simply longer, and that seems to be a
larger issue for the local LLM." The v4 data agrees on the reasoning side: prompts are 10-19 KB (3-5k tokens, no
context pressure), but every local runaway spends 20k+ reasoning tokens holding a long clause list before writing
anything, while v3's short specs passed 46/48 on the same quant; the fp8 reference's worst task is also the longest
(56_tmpl, 19.2 KB, 0/3). Proposed v5 authoring rule, number to be set from results/length-study/report.md:
- prompt.md ceiling: the GLM length study (results/length-study/report.md, 13:53) finds clause count uncorrelated
  with score for every model and the local collapse to be the harness cap, with only Haiku measurably hurt by raw
  bytes (rho -0.82); it proposes <= ~14 KB and <= ~45 top-level clauses as a conservative guard. v5 tasks modelled
  on real requests should sit far below that (a few KB); difficulty comes from one deep, exactly specified
  mechanism, a trap, hidden state or a tool interaction, never from clause count;
- prompt_overhead_tokens (F4) recorded on every run so the ceiling is measured, not assumed;
- a task over the ceiling is split or rejected at authoring time, before any gate run.
