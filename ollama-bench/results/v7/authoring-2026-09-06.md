## 3. How rung 0 was made structural rather than hoped for

Calibration's finding was not that the tasks were easy. It was that the material was never
opened: 4-27% of the window and 9-55% of the material, on a median of four file reads out of a
91-95 file tree (D7-32). The authoring brief's acceptance rule tested that no single grep token
finds the answer; it never tested that a handful of targeted reads cannot assemble it.

So every task in this round has the same structural property, and it is the property rather
than any one puzzle that does the work: **the answer is a set or a value computed over every
stage in the tree, and membership turns on a comparison between two artifact kinds.** A
component document's configuration table is markdown; a module constant is a Python
assignment; a migration date is a CSV field; a ruling is prose. Those four shapes share no
token, so no single grep gathers them, and the stage set is not in the prompt, so no targeted
read finds them either. The traversal is not decoration around the answer; it *is* the answer.

That is what puts the expected coverage where it is. A solver that reads the two files it can
guess at gets nothing at all.

### The check that would have caught the old failure

`authoring/r2/check_rung0.py` is the mechanical test of plan section 2.1, and it is new. It
fails a candidate whose prompt names an undeclared load-bearing file, whose whole answer sits
in one file, or whose answer is reachable by one **selective** grep over the prompt's own
words — a word that hits most of the tree is traversal spelled differently and does not count.
A `LOAD_BEARING` entry may declare `"named_in_prompt": true` for a pointer the prompt
legitimately gives, and every such declaration is printed, so which doors the prompt opens is a
fact in the artifact rather than the author's word.

## 4. The two fields the gate needed, and where they came from

Plan section 2.5: *"Two additions have to be made, and the gate works without neither."* Both
were made.

**`files` in `MANIFEST.json`** — a map of seed path to token count, at the suite's own 4.664
characters per token. Written by `authoring/measure_material.py --emit-files`, restamped by
`authoring/stamp_manifests.py`, which now takes directory arguments so the suite copies stay in
step. All twenty round-1 suite manifests were restamped: **`material_tokens` and `seed_files`
did not move for any of them**, so the map is an addition and not a correction.

**`read_paths` in each pibench run record** — the sorted set of distinct material paths a
trial's `tool_execution_start` events named. Three fields were added, not one:

| field | what it is |
| --- | --- |
| `read_paths` | exact manifest files a tool call named. **This is the gate's number.** |
| `read_paths_expanded` | plus what a directory or glob token named. An upper bound, reported and never gated: `grep -rn x docs/` pulls matching lines into context, not whole files. |
| `tool_arg_keys` | every event key that carried a string, so the argument key is **read off the live stream and never guessed**, exactly as 2.5 requires. |

The scanner does not guess a key. It walks whatever the event carries, records the keys it saw,
and scans every string against the task's own file list — so after the first live cell the key
that carried the paths is a fact in the artifact rather than an assumption in the code. It
covers `bash` as well as `read`, because 1.2 measured a model traversing by `cat` and `grep`:
`m09-main-glm`'s first pass carried nine `bash` calls, one `write` and **no `read`**.

**One deliberate departure from the plan's wording, and the reason.** Section 2.5 says every
path is "normcased". `os.path.normcase` lowercases on Windows and is the identity on POSIX, so
a coverage number computed under pibench's Windows interpreter would not equal the one computed
by `coverage_gate.py` under `python3` from WSL. That is D7-31's fork exactly, one instrument
along. Both sides are therefore folded with an explicit `.lower()`, which is the same
normalisation on both interpreters. The graders' own scope gates still use `os.path.normcase`
on **both** sides, as 4.1 requires, because those comparisons happen inside one process.

## 6. The one command that starts the GPU round

```
setsid -f bash /mnt/d/local-llm-bench/ollama-bench/results/v7/run_gpu_round.sh --go \
  < /dev/null > /mnt/d/local-llm-bench/ollama-bench/results/v7/gpu-round.log 2>&1
```

Detached, because this harness kills long-lived background tasks on a spurious low-memory
signal at 80-90 s (plan section 6.1). Then poll the marker files, never a process name:

```
ls /mnt/d/local-llm-bench/ollama-bench/results/v7/.r2-*-done
```

**Without `--go` it runs nothing.** The default is a dry run that performs every check that
does not need the card, prints the four commands it would run, and exits — so the same script
is both the preflight and the launch, and there is no second thing to keep in step:

```
bash /mnt/d/local-llm-bench/ollama-bench/results/v7/run_gpu_round.sh
```

What `--go` does, in order, with a marker after each:

1. **the GPU proved by a real load**, six tags, never a version string (D7-28) — `gpuverify.sh`;
2. **`read_paths` validated on a live cell** before anything is gated on it: one trial of
   `m09-main-glm` on the workhorse, re-run rather than re-parsed because the stored records
   hold no raw events (2.5), then `validate_read_paths_live.py` checks the new field against
   that record's own `tools` histogram. **If it fails, the script stops and the sweep does not
   run**, because a gate that cannot be read makes the sweep uninterpretable;
3. **the acceptance sweep**: one workhorse trial per candidate on `q27-IQ2_M-64k`, at the baked
   tag, with the pi resilience extension and `WSLENV` set exactly as calibration ran it;
4. **the gate**, read before any pass rate.

About an hour of card time: nine main-band trials at calibration's measured median wall of 41 s,
plus the validation cell and the six-tag load check.

Ending the round is the manager's (owner's ruling 8.3). The script says so and stops.

## 7. Manager's decisions, taken and recorded

1. **One generated grader body for all nine candidates**, from `r2/common.py`, rather than nine
   hand-rolled ones. The defect that nearly invalidated the campaign was one line repeated by
   hand in three graders; one body has one place to be wrong, one place to be fixed, and is
   probed once for all nine. The cost is a systematic risk and it is stated here rather than
   discovered later. Rung 0 is a property of the material, and nine bespoke graders buy nothing
   on the axis this round exists to move.
2. **The expected answer is measured from the seed on disk, never asserted.** Each spec's
   `facts()` reads the tree back after its own overlay and asserts its own arithmetic. The most
   expensive defect this benchmark has had is a reference asserting a fact the material does not
   state, twice; this makes that shape unwriteable rather than forbidden.
3. **Round-2 candidates are not staged into `authoring/suite/`.** The suite is what
   `assemble_suite.py` writes from the register, and a candidate that has not cleared the gate
   is not accepted. The sweep runs against `authoring/r2/gate-suite/`, a staging copy, because
   pibench takes one `--tasks-dir`.
4. **`.lower()` rather than `os.path.normcase` for coverage attribution** — section 4.
5. **Mode 7 keeps its single hard-to-find site.** AUTHORING-BRIEF section 7 says five sites is
   underspecified rather than hard and this benchmark has already lost a task that way. Rung 0
   is carried by *which* symbol to rename, which needs the sweep, not by how many places it
   appears.
6. **Mode 8's budget is declared as a `tool_calls` ceiling and an `out_tokens` ceiling, never a
   turn count**, per plan 4.1, and both are marked provisional in `NOTES.md` pending
   re-derivation from the reference arms' measured median plus 50% in phase 5. D7-40 measured
   the old turn budget wrong on four trials out of four; a number that has never been measured
   is not improved by being restated confidently.
7. **`probes.json` was folded into `selfcheck.py`.** AUTHORING-BRIEF section 3 says a candidate
   directory holds those seven files "and nothing else", and the near-miss set is generated, so
   it is generated *into* the checker rather than beside it.

## 8. What is not done, and what is genuinely open

1. **Family provenance.** Plan 3.2 fixes each slot's family, and the 40% cap arithmetic depends
   on it: glm 8, claude 6, luna 6. The slot names here are those assignments. But real family
   authorship needs `codex-run` for Luna and `pi-run`/`z-run` for GLM, and a worker cannot start
   another worker — those refuse a nested run. **These nine candidates were drafted under the
   manager by clean-context Sonnet subagents, with no agent checking a task it wrote.** The
   family labels are therefore the plan's slot assignments and not a claim about which model
   wrote the prose, and this page says so rather than letting the register imply otherwise.
   *The owner's or the control session's call:* accept the drafts as this round's authoring with
   the provenance footnoted, or re-run phase 1 per family through the three plans using these
   specs as briefs.
2. **Phase 2, blind cross-review by the other two families, is still owed** on all nine,
   whichever way 8.1 above goes. Plan 3.1 requires **two** reviewers to pass a candidate before
   it enters the suite, and 7.1 requires the same of any replacement.

   What was done is **one** round of cross-review, by clean-context agents, none of them
   reviewing a task it wrote. That is short of the plan's rule and the shortfall is the point of
   this item — but it is not nothing, and pretending otherwise would misrepresent where the
   round's value came from. **Every one of the nine came back REVISE.** Three findings were
   systemic rather than local, and none of them was found by any of the mechanical checks:

   - **The index leak.** `make_corpus.py` writes each stage's `limit` and `window_s` into five
     agreeing artifacts, two of which — `config/manifest.json` and `docs/operations.md` — list
     every stage in one small file. Seven of the nine had built their decisive predicate on
     exactly that pair, so "the document disagrees with the module" was answerable from two
     small files without opening a single module. Found on one slot, then measured to be
     systemic, then closed everywhere. `r2/check_index_leak.py` is the standing check and is
     new; a later independent audit re-derived the result with its own detector rather than
     re-running mine, and confirmed the fresh property is written for **every** stage in every
     slot — which is the way this particular fix would most naturally have gone wrong.
   - **Tools that print the answer.** m04's own fixture builder swept the tree and printed the
     result, so a minimal solve read three files. Closing it dropped that slot's expected
     coverage to 41.2%, *below the gate it would have to pass* — the fix exposed a second
     defect — and the slot was redesigned again to make its decisive property joint between
     document and module, which restored it to 77.9%.
   - **Claims the material did not support.** `m09-main-luna` — this manager's own slot — said
     in `NOTES.md` that the deciding glossary entry sat past line 200 of its file. The file was
     106 lines long and the entry was at line 61, and there was no long-command-output component
     at all, so AUTHORING-BRIEF section 7's definition of the mode was simply unmet. Both
     placements are now **build-time assertions**: the build fails rather than the page lying.

   The third is the one worth carrying into the next brief. Two of the three came from a
   reviewer checking a number instead of reading an argument, and in each case the argument was
   excellent and the number was wrong. *The owner's or the control session's call:* accept one
   round of clean-context cross-review as sufficient for a set of candidates that has not yet
   entered the suite, or hold the nine until the second family review the plan asks for.
3. **The section-2.4 thresholds are still unmeasured.** Six seed paths, three hops and five
   touched are the plan's own proposed numbers and it says in terms that no measurement backs
   them. Re-deriving all three from the first sweep's measured `read_paths` distribution is the
   round's first calibration item, and `coverage_gate.py` carries them as three named constants
   at the top of the file so the re-derivation is a one-line change.

   **A specific asymmetry the first sweep should settle.** `LOAD_BEARING_TOUCHED` is an
   absolute five, but the declarations range from 7 paths (`m08-main-claude`) to 18
   (`m01-main-glm`). So the same constant asks m08's trial to reach **5 of 7** of its declared
   paths, 71%, and m01's to reach **5 of 18**, 28%. Both are honest declarations — m08's answer
   genuinely turns on seven artifacts and m01's on eighteen — so the unevenness is in the
   threshold, not in the tasks. Two readings are available once there is data: keep the
   absolute five, which treats "reached five load-bearing files" as an absolute floor on
   traversal and accepts that a narrow task is judged harder; or make it a fraction of the
   declaration, which treats each task's own declaration as the scale. I have deliberately
   **not** chosen: with no measured `read_paths` distribution either choice is a guess, and the
   plan says in terms that these numbers are unbacked. It is recorded here so the choice is
   made on the sweep's evidence rather than discovered as a surprise when m08 fails a gate that
   m01 passes on the same behaviour.
4. **`validate_all.py`'s perturbation adjudication is weaker than it looks**, and this is a
   finding rather than a change. It treats a perturbation as adjudicated when `NOTES.md`
   contains a matching keyword *and* any of `must fail`, `adjudicat`, `stated` or `legitimate`.
   The word "stated" appears in substantially every `NOTES.md` ever written for this benchmark,
   The word "stated" appears in substantially every `NOTES.md` ever written for this benchmark,
   so that half of the test is effectively always on. The *keyword* half is not, and on the
   final run it did real work: it reported `m10-main-glm`'s `extra_trailing_nl` row as
   unadjudicated, because that task's `NOTES.md` said "adding or removing a trailing newline"
   and the table for that key looks for "two trailing newlines" or "an extra trailing newline".
   The adjudication was sound and the prose was loose. Rather than widen the table I made the
   prose exact — m10's `NOTES.md` now names all four failing perturbations one by one — because
   a looser matcher would have let the next loose adjudication through, and naming them is
   what makes the claim checkable at all.

   So the instrument is weaker than it looks in one half and sharper than expected in the
   other. Nothing was changed in it: it is round-1's, and this round's candidates are also
   checked by their own `selfcheck.py`, which asserts an exact verdict and an exact score for
   every case. Worth a look before the next round trusts the `stated` clause.
5. **The ZCode arm (8.2) is phase 5**, not this round. `authoring/run_zcode_arm.py` exists from
   round 1, runs strictly one trial at a time, and gates every launch at 85% of the five-hour
   window. Nothing here changes it.
6. **`sanity.py` still defaults its sandboxes inside the repository** (calibration section 7,
   item 5). Unchanged and still true; `V7_SANDBOX_ROOT` still has to be set before any arm.
7. **`make_corpus.py` writes a dangling `docs/policy/` pointer** into every candidate's
   `README.md` and `docs/operations.md`. No candidate has ever had that directory. It is a
   reader confusion rather than a shortcut, and it is *not* this round's doing — but a reviewer
   found it while reading `m09-main-luna`, where the confusion is sharpest because that task
   really does have a `docs/policy-records/` and really does send a reader looking for it. It
   is corrected there, in that candidate's overlay only. **The other eight still carry it**, and
   the generator is shared and was not touched, because a wart fixed in one of nine places is
   worse than a wart: it makes the nine trees differ for a reason no one will remember. The
   right fix is one line in `make_corpus.py` and it belongs to whoever next has a reason to
   regenerate all nine.
8. **Build artifacts had accumulated in four candidates' material, and one of them regenerated
   itself.** `validate_all.py` found `__pycache__` and `.pytest_cache` inside `seed/` in
   `m03-main-luna`, `m04-main-glm`, `m08-main-claude` and the round-1 `m05-cheap-glm` — residue
   of authors and reviewers running the seeds' own tests while checking their work. Nothing
   measured depended on it: `walk_rel`, `measure_material.py` and every generated grader all
   skip those directory names, so no manifest, token count or seed hash moved when they were
   removed, and every candidate's figures are byte-identical before and after. They were
   removed anyway, because material that carries the residue of its own authoring is not the
   tree the model is supposed to be given.

   `m04-main-glm`'s came back on the next build, which is the part worth recording. Its
   `facts()` imports the seed's own `tools/run_checks.py` to derive the ground truth from the
   very code the task will run — exactly the right way to author a mode-4 task — and the import
   wrote bytecode beside the source. The fix is in the spec rather than in a cleanup sweep:
   `sys.dont_write_bytecode` for the duration of the import, and the cache removed in a
   `finally`. A sweep would have passed the check and left the cause; this way the next build
   on any host produces a clean tree.
