# Benchmark plan, v6 — the quant sweep for usable context

*Written 2026-09-05 by the control session, on the owner's ruling of the same day. The v5 suite
is frozen: no task, checker or band changes in this campaign. What moves is the quant roster and
the context each quant can actually carry.*

## 0. The ruling this plan carries

**A quant is viable on this desktop only if it runs 48k context with no performance
degradation. 64k is better. Find how much more each viable quant can carry.** That is the
owner's floor, and it is what turns v5's finding into a selection rule.

The v5 finding it rests on (`results/v5/findings-2026-09-05-large-band.md`,
`ansible-slb:org/local-llm-bench-desaturation-2026-09-05.md`): on this 16 GB card the bend is a
headroom bend, not a quality bend. Below about 13.5 GB resident the large band runs at
conversational speed; above about 14.7 GB the same work takes six to twenty-five times longer
while still reporting 100% GPU and 66/66 layers. The three 3-bit quants v5 ran were all over the
line at 64k, so v5 never compared 3-bit *quality* at length — it compared 3-bit *spill*.

"No degradation" is measured, never inferred: resident size from `/api/ps` under the
fair-weather line (about 14.2 GB), **and** generation tok/s on the quant's own curve at a fill
near the cell's `num_ctx`. On Windows/WDDM an oversized allocation raises no error and spills
silently; the tok/s check is the one that catches it (v5 plan rule 7).

## 1. Mission

For each candidate quant of Qwen3.8-27B: the largest context it carries without degradation,
and its quality on both v5 bands at that context. Output: a table with one row per quant —
max viable context, resident size, gen tok/s at fill, tiny-band and large-band pass rates,
confidently-wrong rate, wall — and the local roster rows for `org/models.md`.

## 3. The context ladder

48k, 64k, 96k, 128k, then 192k and 256k for any quant still under the line at 128k. The
model's trained window is 262,144 (`ollama show q27-Q2_K_L`, architecture `qwen35`), so every
rung is inside it. Each cell is an Ollama tag `q27-<QUANT>-<ctx>` baked with
`make_model.sh <QUANT> <num_ctx>` (the script has no context suffix; name the tag explicitly
as v5 did).
KV cache stays q8_0 with flash attention on, which is the machine's own setting; v5 measured
q4_0 KV at identical resident sizes and withdrew it, so it is not a lever here.

## 4. Phases and run order

**Phase 0 — placement, GPU only, about five minutes per cell.** For each quant, climb the
ladder from 48k: bake the tag, load it, read `/api/ps` (resident, `pct_gpu`), then measure gen
tok/s at empty context and at a fill near `num_ctx` (`gpu_verify.py`'s method; `pibench.py
tps_curve` is the same code). A cell passes if resident is at or under 14.2 GB and gen tok/s is
on the quant's curve. Stop climbing at the first failing rung. A quant whose 48k rung fails is
out: `ollama rm` every tag, note it in `decisions.md`, move on. Q3_K_S and IQ3_M start here and
probably end here.

**Phase 1 — quality sweep, one trial per cell.** Every surviving quant runs the tiny band at
24k (`results/v5/authoring/round2/suite-0`, `--num-ctx 24576`) and the large band at its
largest passing rung up to 64k (`results/v5/authoring/round3/suite`). The v5 working-margin
rule stands: a task runs only in a cell whose `num_ctx` is at least 1.6x its material, so a
48k-only quant runs the three large-band tasks that fit and is reported as such, never padded.
`--think medium --trials 1 --no-tps --timeout 900`. Both bands may run back to back on one
quant; never two quants at once on the GPU.

**Phase 2 — the verdict rows, three trials.** The best two quants by phase 1 (pass rate first,
then confidently-wrong rate, then wall) run both bands three times at their largest passing
rung up to 64k. These are the rows the report is written from.

**Phase 3 — the stretch.** Each phase 2 quant whose ladder passed 96k or 128k runs the large
band once more at that rung. Quality should not move; the point is a measured cell at the
larger context, so that the roster row can name it.

Order: phase 0 for every quant before any phase 1, because phase 0 is what prunes the disk.
Then phases 1-3. Resume rather than repeat: `pibench.py` resumes from an existing tag's JSON.

## 5. Verdict rule

v5 section 6 stands in full and is not restated: task-level, two of three trials under the
900 s wall, viable at three of four headline tasks and marginal at two, the confidently-wrong
rate reported beside the pass rate. Add one column: **max viable context**, from phase 0, which
is the number this campaign exists to produce.

## 6. Budget

GPU: phase 0 about 2 h (up to ten quants, two to three rungs each); phase 1 about 5 h (sixteen
tasks per quant at one to three minutes each); phase 2 about 3 h; phase 3 under 1 h. About
11 h, which is one overnight. No reference-model spend: the v5 Haiku and Sonnet rows are the
reference and are not re-run. OpenRouter is not involved.

## 7. Traps, each with its workaround as the instruction

- **Verify the GPU by load, never by version.** A real generation reporting `pct_gpu` and a
  tok/s on the curve, before the first scored trial and after any Ollama restart
  (`ansible-slb:org/ollama-cuda-repair-2026-09-04.md`).
- **The Windows daemon is the one with the models.** A WSL-side `ollama serve` holds
  `127.0.0.1:11434` inside WSL with zero models. Drive Windows Ollama through
  `/mnt/c/Users/slb/AppData/Local/Programs/Ollama/ollama.exe` from WSL, and run `pibench.py`
  through the Windows interpreter as `run_bend_large.sh` does — no ssh.
- **Resident size from `/api/ps`, never `nvidia-smi`**, which reads about 1.8 GB higher and
  would fail every cell (v5 D-R3-9).
- **No OOM is raised on WDDM.** Spill shows only as tok/s off the curve. Record tok/s on every
  phase 0 cell and flag any scored trial whose tok/s is below its quant's placement figure.
- **Never poll with `pgrep -f`**; poll the artifact (the JSON reaching N completed tasks).
- **Unload Ollama before any direct `llama-server` probe**; its runner shares the binary name.
- **Remove failed quants immediately.** The disk cannot hold the roster and the failures.
