# Benchmark plan, v6 — the quant sweep for usable context

*Written 2026-09-05 by the control session, on the owner's rulings of the same day; revised the
same evening with the data fields, the tighter timeouts and the reject-early ordering. The v5
suite is frozen: no task, checker or band changes in this campaign. What moves is the quant
roster and the context each quant can actually carry.*

## 0. The rulings this plan carries

1. **A quant is viable on this desktop only if it runs 48k context with no performance
   degradation. 64k is better. Find how much more each viable quant can carry.**
2. **No run that spills to CPU-speed generation is viable**, so the timeouts are cut to what a
   healthy cell needs, and a trial that runs past them is a rejection signal, not a data point
   to wait for.
3. **Spend the night on the measurements most likely to reject a quant first**, so a rejected
   quant is off the disk and replaced by the next candidate while the GPU is still busy with
   something useful.

4. **Every v6 row runs under the new pi harness, and nothing runs until it is deployed.** The
   fleet's pi harness is gaining middle-preserving tool-output truncation (24k characters,
   8k kept each side) and a provider-error retry, loaded as an extension. A local model at 64k
   sees a different conversation once tool output is cut, so **v5's local rows were produced
   by a different harness and are superseded, not compared against.** `pibench.py` runs pi
   directly with `--no-extensions`, which still honours an explicit `-e`, so the harness
   change reaches the bench through one addition: an option that appends `-e <path>` to pi's
   argument list, pointing at the deployed extension (`~/.claude/skills/pi-run/scripts/
   pi-resilience.ts`; on Windows `C:\Users\slb\.claude\skills\pi-run\scripts\
   pi-resilience.ts`). The manager does not start phase 0 until the control session says the
   harness is deployed and that option exists in this clone. There is no point measuring a
   harness that is about to change.

The v5 finding they rest on (`results/v5/findings-2026-09-05-large-band.md`,
`ansible-slb:org/local-llm-bench-desaturation-2026-09-05.md`): on this 16 GB card the bend is a
headroom bend, not a quality bend. Below about 13.5 GB resident the large band runs at
conversational speed; above about 14.7 GB the same work takes six to twenty-five times longer
while still reporting 100% GPU and 66/66 layers. The three 3-bit quants v5 ran were all over
the line at 64k, so v5 never compared 3-bit *quality* at length — it compared 3-bit *spill*.

"No degradation" is measured, never inferred: resident size from `/api/ps` under the
fair-weather line (about 14.2 GB), **and** generation tok/s on the quant's own curve at a fill
near the cell's `num_ctx`. On Windows/WDDM an oversized allocation raises no error and spills
silently; the tok/s check is the one that catches it (v5 plan rule 7).

## 1. Mission

For each candidate quant of Qwen3.8-27B: the largest context it carries without degradation,
its speed at that context, and its quality on both v5 bands there. Output: one row per quant
with every field in section 5, and the local roster rows for `org/models.md`.

Removed 2026-09-05 as not viable under ruling 1: Q3_K_M (14.91 GB resident at 48k, measured,
degraded) and Q3_K_L (never fit at a useful context). Every tag of each was removed.

**The reserve** is `results/v6/reserve.md`: a ranked list of not-yet-pulled candidates from
the publisher sweep (unsloth UD dynamic quants, mradermacher i1 imatrix quants, any Qwen3.8-27B

quant is rejected, the manager removes it and pulls the top reserve entry **in the background
while the GPU runs the next quant** — a pull is network and disk, and never contends with a
trial. Cap the live roster at ten. Every swap goes in `decisions.md`.

**Disk is the constraint, not the GPU.** Models live on `C:` (`~/.ollama/models`), about 17 GB
free after the four pulls. A rejected quant is removed with `ollama rm`, every tag, before the
next pull starts. Moving `OLLAMA_MODELS` to `E:` (1.4 TB free) is a host configuration change
and belongs in ansible-slb; it is recommended to the owner in section 10, not required here.

## 3. The context ladder

48k, 64k, 96k, 128k, then 192k and 256k for any quant still under the line at 128k. The
model's trained window is 262,144 (`ollama show q27-Q2_K_L`, architecture `qwen35`), so every
rung is inside it. Each cell is an Ollama tag `q27-<QUANT>-<ctx>` baked with
`make_model.sh <QUANT> <num_ctx>` (the script has no context suffix; name the tag explicitly
as v5 did). KV cache stays q8_0 with flash attention on, which is the machine's own setting;
v5 measured q4_0 KV at identical resident sizes and withdrew it, so it is not a lever here.

## 4. Timeouts and the speed gate

Healthy v5 cells needed: tiny band 9-185 s per task, large band 35-494 s (Q2_K_L at 64k, the
longest being g03 with two length stops). Degraded cells needed 216-1780 s. So:

| band | `--timeout` | v5 was |
| --- | ---: | ---: |
| tiny, 24k | 300 s | 900 |
| large, 48k-64k | 600 s | 900-1800 |
| stretch, 96k and up | 600 s | — |

A trial that times out is recorded as `timed_out` and counts as a fail, and **two timeouts on
one quant in phase 1 reject the quant** without finishing its row. The point of the cut is
ruling 2: a cell that needs longer than this is generating at spill speed, and the answer it
would eventually give is not one anybody can use.

The speed gate, applied in phase 0 and re-checked on every scored trial: gen tok/s at a fill
near `num_ctx` **at or above 35 tok/s passes**; **below 20 tok/s is spill and rejects the
cell**; between the two is marginal — record it, keep the cell only if no better rung exists,
and say so in the row. Q2_K_L's known curve is 58 tok/s empty and 51 at 27k fill; IQ3_M
measured 41 at 60k in the gpu-tune study. Prompt tok/s at the same fill is recorded beside it;
it is not gated, but a prompt rate under about 500 tok/s at 64k makes an agentic turn wait
over a minute on prefill alone and belongs in the row.

## 5. Data to record

**Per placement cell (phase 0)**, into `results/v6/placement.json` and a rendered `.md`:
quant, `num_ctx`, resident GB (`/api/ps`), `pct_gpu`, `nvidia-smi` peak MiB (recorded, not
used for the verdict), load time, gen tok/s at empty context, gen tok/s at a fill of about
90% of `num_ctx`, prompt tok/s at that fill, time to first token at that fill, and the
pass / marginal / spill verdict.

**Per scored trial**, which `pibench.py` already writes: task, band, cell, pass, score,
verdict (`correct` / `visibly_failed` / `confidently_wrong`), wall s, in tokens (sum over
turns), peak prompt tokens (the context the task actually reached), out tokens, turns, tool
calls, stop reasons, `timed_out`, resident GB and `pct_gpu` during the trial, `nvidia-smi`
peak, and **achieved out tok/s = out tokens / wall**, which folds prefill and tool time in and
is the number a user feels.

**Per quant summary**, the row the report is built from: max viable context; resident and gen
tok/s at that context; gen tok/s at 64k for comparability; pass rate per band; confidently-
wrong rate; median and max wall per band; mean in, peak-prompt and out tokens per task; mean
turns and tool calls; timeouts; and the verdict word from section 7.

Two things pibench does not record and this campaign does not chase: GPU power and
temperature (the card runs at 100% for the night regardless) and per-turn latency
(peak-prompt tokens and achieved tok/s stand in for it).

## 6. Run order — reject early, replace while running

Phase 0 is cheap (about five minutes a cell) and phase 1 is not (about 40 minutes a quant), so
the night is spent in this order, and the manager re-plans after every rejection.

**A. Placement, all quants, most-informative first (about 2 h).** The question the campaign
exists to answer is whether any 3-bit quant carries 64k, so: IQ3_XXS at 64k, then IQ3_XS at
64k; then IQ2_M up the whole ladder (it is the one that may reach 128k or more); then Q2_K,
then Q2_K_L from 96k up; last Q3_K_S and IQ3_M at 48k only, which are expected to fail and are
placed last so their failure costs nothing. A quant that fails 48k is rejected on the spot:
`ollama rm` every tag, start the top reserve pull in the background, note both in
`decisions.md`.

**B. Sentinels, every surviving quant, one trial each (about 15 min a quant).** Two large-band
tasks at the quant's top rung up to 64k: `t03` (30.6k tokens of material; it is the task that
exposed the bend, 35 s healthy against 216-881 s degraded) and `g03` (the hardest; the only
task Q2_K_L missed). Reject a quant whose t03 wall is over 3x Q2_K_L's at the same rung, or
that times out either. Order the survivors best-first by t03 wall for everything that follows,
so that if the night runs short the strongest candidates have complete rows.

**C. Phase 1, one trial, both bands, every survivor at its top rung up to 64k.** The v5
working-margin rule stands: a task runs only in a cell whose `num_ctx` is at least 1.6x its
material, so a 48k-only quant runs the three large-band tasks that fit and is reported as such,
never padded. `--think medium --trials 1 --no-tps`, timeouts from section 4. Two timeouts on a
quant reject it mid-row. Never two quants at once on the GPU; a background pull is fine.

**D. Phase 2, three trials, the best two.** By pass rate, then confidently-wrong rate, then
median wall. Both bands at the top rung up to 64k. These are the verdict rows.

**E. Stretch.** Each phase 2 quant that placed at 96k or above runs the large band once at its
top rung. Quality should not move; the point is a measured cell at the larger context so the
roster row can name it.

Resume rather than repeat: `pibench.py` resumes from an existing tag's JSON. Phase 0 results
are a JSON the manager appends to, never rewrites.

## 7. Verdict rule

v5 section 6 stands in full and is not restated: task-level, two of three trials under the
wall, viable at three of four headline tasks and marginal at two, the confidently-wrong rate
reported beside the pass rate. Two additions: the **max viable context** column from phase 0,
and the section 4 timeouts replace the 900 s wall wherever v5 names it.

## 8. Budget

GPU: A about 2 h, B about 1.5 h, C about 4 h (six survivors at 40 min), D about 3 h, E under
1 h. About 11 h, one overnight, with the rejections in A and B buying the time for D and E. No
reference-model spend: the v5 Haiku and Sonnet rows are the reference and are not re-run.
OpenRouter is not involved.

## 9. Traps, each with its workaround as the instruction

- **Verify the GPU by load, never by version.** A real generation reporting `pct_gpu` and a
  tok/s on the curve, before the first scored trial and after any Ollama restart
  (`ansible-slb:org/ollama-cuda-repair-2026-09-04.md`).
- **The Windows daemon is the one with the models.** A WSL-side `ollama serve` holds
  `127.0.0.1:11434` inside WSL with zero models. Drive Windows Ollama through
  `/mnt/c/Users/slb/AppData/Local/Programs/Ollama/ollama.exe` from WSL, and run `pibench.py`
  through the Windows interpreter as `run_bend_large.sh` does — no ssh.
- **Resident size from `/api/ps`, never `nvidia-smi`**, which reads about 1.8 GB higher and
  would fail every cell (v5 D-R3-9).
- **No OOM is raised on WDDM.** Spill shows only as tok/s off the curve. Record tok/s on every
  phase 0 cell and flag any scored trial whose achieved rate is far below its placement figure.
- **Never poll with `pgrep -f`**; poll the artifact (the JSON reaching N completed tasks).
- **Unload Ollama before any direct `llama-server` probe**; its runner shares the binary name.
- **Remove failed quants immediately, then pull.** The disk cannot hold the roster and the
  failures at once.
- **A pull and a trial may overlap; two trials may not.**

## 10. Standing rules for the manager

Every decision in this plan is the manager's, recorded in `results/v6/decisions.md` as taken,
including every rejection and every swap from the reserve. Nothing here is gated on the owner.
Write `results/v6/handoff-<date>.md` at the end of the session with the section 5 summary table
so far, the next run, the disk state, and the models left on the daemon. Do not touch the v5
suite directories except to read them. Commit and push `local-llm-bench` after each phase with
a one-line lowercase message.

## 11. What is genuinely the owner's

- **Whether the Haiku and Sonnet reference rows are re-run under the new harness.** They were
  produced by the old one, and a verdict compares local against reference under the same
  harness; truncated tool output changes what the reference model sees too. Recommended: yes,
  three Haiku and two Sonnet trials on both bands, before phase 2 so the verdict rows have a
  like-for-like reference. It is API spend and it is not GPU time, so it can run beside phase 0.
- Whether `OLLAMA_MODELS` moves to `E:` through ansible-slb. Recommended: yes, before v7,
  because the C: ceiling forces the delete-as-you-go rule.
- Whether a quant that passes only 48k is worth keeping on disk after the campaign.
- When the campaign ends and the report is written.
