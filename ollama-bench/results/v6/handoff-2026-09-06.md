## The campaign in one paragraph

Nine quants of Qwen3.8-27B were placed on an RTX 5080 (16 GB) for the largest context each
carries without degradation, then scored on the frozen v5 suite under the new pi harness. **No
3-bit quant of any publisher carries 64k on this card.** Every quant that does is a 2-bit quant,
and the only one that reaches **96k** is `IQ2_M` — the smallest and most aggressively quantised
file on the roster. The ordering by context reach is the **exact inverse** of the ordering by
bits.

## The visibly-failed rate, and why the bare number misleads

v5 recorded **one** `visibly_failed` in its entire campaign and **zero** across thirty-two
tiny-band trials. v6 is at **6 in 46 (13.0%)**. That is a real shift, and it is **three different
things** (D6-44, D6-45):

1. **Genuine incompleteness** — timed out or `length`-stopped mid-work with nothing usable
   written. The majority.
2. **A correct answer in the wrong shape.** Q2_K_L's t02 at 64k found the right answer — `no`,
   line 77, the exact source line — and wrote `EVIDENCE: release_control/policy_chain.py:77: …`,
   prefixing a **file path** onto a template that asks for `EVIDENCE: <line-number>: …`. Scored
   0/3 on `format`. The checker is **not** at fault (it tolerates CRLF, blank lines, surrounding
   whitespace) and the suite is frozen, so nothing was changed — but "produced the right answer
   in the wrong shape" and "produced nothing" are opposite outcomes for a delegating user.
3. **A length cap intercepting confident wrongness.** Of 44 trials analysed, 7 (16%) hit a length
   stop. Those 7 averaged **17,210 output tokens against 5,041** for the rest — and **not one of
   them was confidently wrong** (4 correct, 3 visibly failed), while all 6 confidently-wrong
   verdicts came from trials that finished inside their budget. The cap looks like a **safety
   valve**: a run generating 3.4x the normal volume is on its way to a fluent wrong answer, and
   truncation turns that into a failure the user notices.

**So part of v6's excess visible failure is confident wrongness being downgraded into the cheap
failure mode, which is the direction you want.** Quote the breakdown, never the bare rate.

## Two caveats that constrain every quality number here

1. **The scored rows do not fill the window they are placed in** (D6-30). Peak prompt reaches
   **25–39% of a 64k cell** — g03 hit 25,748 tokens of 65,536, t03 16,502. v5 withdrew synthetic
   fill, and the pi-resilience extension middle-truncates tool output above ~5,100 tokens. So
   placement measures capacity honestly, but a 64k row and a 48k row run at similar occupancy:
   **the quality-versus-context comparison is weak by construction.** "Quant X is accurate at
   64k" means "at 64k of *configured* window and ~26k of *used* window". Report max viable
   context and quality as two separate findings.
2. **This GPU has been shared since 22:44** (D6-38). Every wall-clock number after that time was
   taken alongside the prompt campaign. Contention measures ~6%, and every quant pays it, so the
   quant-versus-quant *ordering* stands — but **no absolute throughput figure from tonight should
   be quoted as this card's capability**, and these walls are not comparable to v5's.

## Downloads — the owner's just-in-time rule

Owner's ruling, 21:45 and 21:50 (D6-28, D6-29): **a pull starts only when the GPU is about to
need that candidate**, never as a background job run ahead of time. Implemented in `phaseDE.py`:
every remaining scored cell is enumerated up front so the campaign's **final** cell is knowable,
and `maybe_jit_pull()` fires at the start of that cell and nowhere else, subject to a **05:45
cutoff** past which it does nothing. `jit_pull.sh` runs the download immediately — overlapping
exactly one trial, which the plan permits — and its **placement waits on `.phaseE-done`** so two
GPU loads never overlap. Nothing else in the tree pulls: `pull2.sh` and `pull3.sh` are dead.

1. **0.41 GB bought a 2.8x speedup.** IQ3_XXS at 64k, projector stripped: 10.3 -> 29.0 gen tok/s

## How to re-attach

All paths absolute. WSL, never ssh. `PY=/mnt/c/Users/slb/scoop/apps/python/current/python.exe`.

**1 — See where the chain is.** The log is the live view; the marker files are the phase record.

```
tail -40 /mnt/d/local-llm-bench/ollama-bench/results/v6/phaseAll.log
grep -aE "^== phase|CELL |PHASE C COMPLETE|PHASES D AND E COMPLETE" \
     /mnt/d/local-llm-bench/ollama-bench/results/v6/phaseAll.log | tail -10
ls -1 /mnt/d/local-llm-bench/ollama-bench/results/v6/.*-done
```

The last `CELL …` line is the cell in flight. Markers appear in order: `.phaseB-done`,
`.phaseC-done`, `.phaseD-done`, `.phaseE-done`. **`.phaseE-done` means the campaign is finished.**

**2 — Confirm it is alive rather than merely quiet.** A single large-band trial may legitimately
run 600 s in silence, and resumed cells write nothing at all.

```
ps -eo pid,args | grep -v grep | awk '$0 ~ /chainAll\.sh|phaseC\.py|phaseDE\.py/ {print}'
nvidia-smi --query-gpu=memory.used,utilization.gpu --format=csv,noheader
```

**GPU near 0% with no chain process is a dead chain. GPU near 100% is a trial running.** That
distinction cost 26 minutes of idle GPU once tonight (D6-41); the waiter
(`results/v6/waiter.sh`) prints GPU utilisation beside its stall alarm for exactly this reason.

**3 — Stop it.** There is no clean cell-boundary pause, and none is needed: **pibench resumes per
`(task, trial)`, so killing costs at most the one trial in flight.** Never kill on the pi package
name — a second campaign runs pi on this machine and `kill_pi.ps1` is scoped by *ancestry* to
processes descended from a `pibench.py … --tag v6-` parent (D6-37).

```
ps -eo pgid,args | grep -v grep \
  | awk '$0 ~ /chainAll\.sh|phaseC\.py|phaseDE\.py/ {print $1}' | sort -u \
  | while read g; do kill -TERM -"$g"; done
/mnt/c/Windows/System32/WindowsPowerShell/v1.0/powershell.exe -NoProfile -ExecutionPolicy Bypass \
  -File 'D:\local-llm-bench\ollama-bench\results\v6\kill_pi.ps1'
```

To see what that would kill, read-only first: `list_node.ps1` by the same invocation.

**4 — Restart it.** Stop-and-start is one command, because doing them separately is how the GPU
went idle for 26 minutes:

```
bash /mnt/d/local-llm-bench/ollama-bench/results/v6/restart_chain.sh
```

It stops the chain, clears v6-owned pi children by ancestry, relaunches `chainAll.sh`, and
**verifies the chain is actually alive**, printing `FAILED TO RESTART -- the GPU is idle, fix
this now` and exiting non-zero if not. Completed trials resume in seconds; nothing is re-run.

**5 — Regenerate the tables from the artifacts** (pure file readers, WSL python is fine):


in the raw JSON may be stale; the rendered tables are authoritative.
